# Extensions

An **extension** is something a person adds to Pistachio that is not Pistachio: a Chrome extension from the Chrome Web Store, one of ours from the library, or one they (or their coding agent) wrote into a folder on this Mac. Every extension lives in one place in the window, **the Ledge** — a strip at the foot of the sidebar's card — and shows up as the verbs the browser already has: a `/` command in the Bar, a tool the agent can call, an entry in a window's ⋯ menu, a keyboard shortcut. A **Pistachio extension** is the new thing: a folder with a `pistachio.json`, drawn in the shell's own frames, run by main as the one broker, with an API (`pistachio.*`) that reaches what a Chrome extension never can — the desk, spaces, captures of windows, the agent, notes, files — under permissions a person approves once and can read in a sentence. The aim is a browser a person builds for themselves: "I wish the browser could X" becomes a folder their agent writes, hot-loaded, reviewed on an approval sheet, and theirs.

Desktop only. Builds on `docs/spaces.md` (spaces, the sidebar), `docs/double-sidebar.md` (the rail and the card), `docs/desk.md` (windows), `docs/desk-agent.md` (the Bar, commands, the agent's tools), `docs/notes.md` §4–5 (shell pages, frames of another origin in the shell), `docs/shields.md` (the request hub, the every-frame preload), `docs/terminal.md` §3 (a utility process beside main). Every section below is normative for the implementation on branch `extensions`. Three ideation passes and three probes on Electron 43.4.1 (2026-10-30) stand behind the decisions; what was measured is marked so.

(The chat agent is called **Pistachio** in the UI — "Ask Pistachio" — and *the agent* here. Jev is the intent model behind routing and the brief, not the agent.)

## 1. Decisions

| # | Decision | Choice |
| --- | --- | --- |
| X1 | **Two kinds, one registry.** | A Chrome extension is a folder with `manifest.json` (MV3), run by Electron's extension system plus `electron-chrome-extensions` (MIT) per Profile session. A Pistachio extension is a folder with `pistachio.json`. Both are rows of `<userData>/extensions.json`, shown on one Ledge, listed on one page. Not: a `pistachio` key inside Chrome's manifest (Chromium owns that validator; Chrome's id is a hash of the path; an agent would write MV3 boilerplate to get a `/` command). |
| X2 | **A Pistachio extension's UI runs in sandboxed `WebContentsView`s on its own partition**, at `pistachio-ext://<id>/…`. | Its **pages are tabs** — `kind: "human"` with an `extensionId` marker (a new kind would miss a hundred `kind === "human"` gates), on `persist:pistachio-ext-<id>` with the extension preload instead of the tab's, `nodeIntegrationInSubFrames` off — so a desk window like any page's, with the desk's stills, flights, minimize and a device-local session restore; one predicate, `isExtensionTab`, keeps Shields, Watchtower, the tab preload, the Profile's session setup, Profile moves, the sync mirror, Chrome's `addTab`, live share, closed-tab memory, Tidy and the agent's page tools out of it. Its **panel** is a view main places over the side card's slot the shell reports (the Glance recipe). Its **worker** is a hidden view. One preload, one transport, three contexts. Not: an iframe in the shell's DOM — a spike showed such a frame gets its own process and no preload, but the shell's renderer is the one unsandboxed process in the app and a frame inside it inherits that; not a `WebContentsView` the desk must cover and still for every surface (pages as tabs need none of that); not extensions shipping React into the trusted shell (a full compromise, and our internals frozen as API). |
| X3 | **Main is the only broker.** | The extension preload exposes one raw wire over two channels (`pistachio-ext:call`, `pistachio-ext:event`) and nothing else; `pistachio` itself is built in the page's own world over that wire (a bridge cannot carry a `MediaStream`, a stream or a port); main derives *which* extension is calling from the sender's view **and** the calling frame's origin — never from the message — and answers through one dispatch table (`EXT_METHODS`) checked against the API's types and one choke point (`ExtensionScope`) that every method reaches the browser through. No extension context can reach a `pistachio:*` channel. |
| X4 | **A worker is optional: `web` in v1, `node` later.** | A `web` worker is a hidden `WebContentsView` in a hidden `BaseWindow` (sandboxed, context-isolated, the extension's partition, throttling off) that loads the extension's `worker` file; it starts on first need and stays up while something holds it. A `node` worker (a utility process under Node's permission model) is the Critical tier and later. Chrome extensions keep their MV3 service workers and never get `pistachio.*`. |
| X5 | **The API keeps Chrome's nouns and a modern shape.** | `tabs.query`, `storage.local.get`, `runtime.sendMessage`; everything a Promise; `onX(fn)` returns an unsubscribe. The manifest declares what exists (commands, tools, menus, pages); code handles events. About forty-five entry points in v1 (§5); later ones stay later until an extension needs them. |
| X6 | **Capabilities are granted at install, in tiers, on one sheet.** | Low (one line), Medium, High (named one by one), Critical (red, a second confirm). A manifest that widens its permissions pauses the extension until approved again; narrowing applies at once. Invoking an extension on a tab grants it that tab (a gesture grant) — the cheap default an agent reaches for first. No cookie API; no extension uses a Profile's cookie jar. Nothing enables itself: not a synced record, not a folder that appeared, not the agent's draft. |
| X7 | **The dev loop is "drop a folder".** | Developer mode (Settings → Extensions) keeps `~/Pistachio/Extensions/` with `AGENTS.md`, `CLAUDE.md`, a skill, the `.d.ts` and the schema; each folder there is watched and hot-reloaded; Pistachio writes `.pistachio/status.json` and `.pistachio/log.ndjson` back into the folder. No CLI and no local socket in v1: files are what every coding agent already reads, and they work with the app closed. |
| X8 | **First-party extensions ship inside the app.** | `apps/desktop/extensions/<id>/` is packaged to `Resources/extensions/<id>/`, signed and updated with the app; they can be turned off, not removed. The Recorder is the first. A library server with signed packages is later. |
| X9 | **The Ledge** is where extensions are seen. | A 36px strip at the card's foot (the free band the person pointed at), the same in Home and every space, sharing its row with the footer's pills. Pinned icons on the leading side, ⋯ to the extensions page. In rail mode a short column at the rail's foot; hidden, it comes with the column. Order is per Profile, never per space. |
| X10 | **Chrome popups are Chrome's; the libraries are patched, not trusted.** | A Chrome extension's action opens `electron-chrome-extensions`' popup: a frameless child window at the icon, closed on blur, exactly Chrome's behaviour and look. Not restyled. The Pistachio-native popup card (pre-warmed, torn off) is later. Both libraries are pinned and patched (`patches/`, §6.5): as shipped they trust a renderer-sent extension id, give `chrome.cookies` to every extension without a check, navigate tabs around our guards, and match the store's origin by prefix. |
| X11 | **Honest installs.** | The Chrome Web Store flow lands on our approval sheet, with a verdict read from the manifest: works / partly works (what differs, in words) / won't work (why, and what to use instead). Shields already blocks ads and trackers: a blocker built on `declarativeNetRequest` or `webRequest` is refused with that sentence, not installed to do nothing. |
| X12 | **The agent and extensions meet both ways.** | A Pistachio extension declares tools (JSON Schema in, JSON out) the agent calls in a tool group of its own; a `/` command can be a prompt template. `/extension <wish>` makes the agent draft one into the dev folder, where it lands paused for the person's approval like any folder. The agent has no install or approve tool. |
| X13 | **The Recorder uses only the public API.** | Tab capture through `getDisplayMedia` in the worker (no macOS permission, 58 fps measured, page audio in stereo), events from main's own hooks plus the tab preload's element rects, mediabunny's fragmented MP4 to disk, an editor in a desk window, WebCodecs export. Whatever it needs that the API lacks, the API gets. |

## 2. What a person does

**See them.** The Ledge sits at the foot of the sidebar's card: each pinned extension's icon in a 28px target, 4px apart; past the room (six at the default card width) they flow into **⋯**, which opens `pistachio://extensions`. An icon shows its badge (Chrome's `action.setBadgeText`, or `pistachio.ui.setBadge`) as a small pill at its top-trailing corner in our shape; dims to 35% where the extension is off in this Profile; carries an amber dot when it needs the person (a permission to approve, a new folder to review) and a red dot when one of the person's own extensions is broken (a store extension's console noise is never surfaced). The empty Ledge is one dashed slot and the word *Extensions*, the twin of the empty Stack's sheet.

**Click one.** A Chrome extension's icon runs its action on the window in use: its popup opens at the icon, or its `onClicked` fires. A Pistachio extension's icon opens its **panel** — a side card beside the sidebar, like the More card, holding the extension's `panel` page under a head the shell draws (its icon and name, never the frame's own) — or, with no panel, fires its `action` event. Right-click: *Options*, *Pin / Unpin*, *Off in this Profile*, *Agent can use it* (when it has tools), *Remove…*; one of the person's own adds *Reload*, *Show folder*, *Logs*. Drag along the Ledge reorders; ⌘⇧E puts the keyboard on the Ledge (←/→ walk, ↵ runs, 1–9 run the nth, ⎋ gives it back).

**Say them.** The Bar's `/` menu gains a group, **Extensions**, after *Open*: each declared Bar command (`/record`, `/prs`) with its hint, and each Chrome extension on the Ledge as `/<name>` (opens its action). A command of kind `prompt` is a request to the agent with the template filled (`{arg}`, `{page.title}`, `{page.url}`, `{selection}`); one of kind `event` wakes the worker. Declared context-menu items appear in the page's menu (and a Chrome extension's `contextMenus` do), grouped under the extension's name past one; `window` items in a desk window's ⋯ menu under *Extensions ▸*. Declared keyboard commands are configurable in Settings → Keyboard under **Extensions**; a suggested key that meets an app key starts unbound and the sheet says so.

**Find and add them.** `pistachio://extensions` is a shell page (opened as a desk window from ⋯, ⌘L *Extensions*, Settings → Extensions, the empty Ledge). Its head is one field, *Search extensions, or describe one to make*; under it: **On this Mac** (installed, each with its icon, a line, where it runs, a switch), **Made for Pistachio** (the library: Recorder first), **Works in Pistachio** (a curated slice of popular Chrome Web Store extensions with their verdicts, added by id with no visit to the store), **Yours** (the dev folder: *Show folder*, *New…*, *Make one with Pistachio*, *Build with Claude Code*), and a foot: *Browse the Chrome Web Store* (opens it in a tab; its *Add to Chrome* button installs here) and *Load a folder…*. A store link pasted in ⌘L offers *Add <name> to Pistachio*.

**Approve one.** Every install, and every reload that asks for more, is one sheet:

```
┌──────────────────────────────────────────────────┐
│ [◉]  GitHub inbox                                │
│      Yours · ~/Pistachio/Extensions/gh-inbox      │
│                                                  │
│  Adds                                            │
│  /prs in the Bar · a tool the agent can call     │
│                                                  │
│  Can                                             │
│  ●  Talk to api.github.com                       │
│  ●  Read and write your notes                    │
│     See everything it declares ›                 │
│                                                  │
│  Agent can use it                     [  On  ]   │
│                                                  │
│                      [ Not now ]  [ Turn it on ] │
└──────────────────────────────────────────────────┘
```

At most four lines, broadest first, a filled dot for a broad reach; Critical lines in red with a second confirm; a Chrome extension's lines come from its permissions in three plain buckets (*Pages*, *You*, *This Mac*) and its verdict replaces the button when it is ✕. A Pistachio extension's lines are fixed phrases per capability (§6.1), never the extension's own words.

**Make one.** `/extension <wish>` in the Bar (or *Make one with Pistachio* on the page, or a plain "make me an extension that…", which routing sends the same way): the agent writes the folder into `~/Pistachio/Extensions/<slug>/` with its draft tools (§8), the Ledge shows a shimmering slot with the extension's monogram while it works, and the folder lands **paused** — the approval sheet with *View code* is the person's click, never the agent's. *Build with Claude Code* opens a terminal tab (docs/terminal.md) in a new folder of the dev folder with `claude` started on the wish; `AGENTS.md` and the skill there tell any coding agent the API, the folder contract and how to read `status.json` after each save.

**Record something.** The Recorder (§9) is the library's first: `/record`, its Ledge icon, or ⌘⇧6 records the window in use after a count of three; the editor opens as a desk window; export is MP4, WebM or GIF to the screenshots folder.

## 3. The manifest

`pistachio.json`, validated by the zod schema in `packages/extension-api/src/manifest.ts` (the one source for the types, main's validator, and `pistachio-extension.schema.json` in the dev folder so an editor validates as the agent types):

```ts
interface PistachioManifest {
  $schema?: string;
  api: 1;                                  // the API major it was written against; N and N-1 load
  id: string;                              // /^[a-z0-9]+(\.[a-z0-9-]+){1,4}$/ — "dev.zach.gh-inbox": stable across moves, the origin's host
  name: string;                            // ≤ 40
  version: string;                         // semver
  description?: string;                    // ≤ 200, on the sheet
  icon?: string;                           // svg or png ≥ 64px, relative; else a monogram
  permissions?: Capability[];              // §6.1
  hosts?: string[];                        // match patterns for net.fetch and pages.read; "<all_urls>" — or any pattern naming every site, "*://*/*" — is Critical
  worker?: { type: "web"; main: string };  // "worker.js" | "worker.ts" (erasable TypeScript, stripped as served)
  panel?: { file: string; width?: number; height?: number };   // the Ledge icon's side card
  pages?: Record<string, { file: string; title: string; singleton?: boolean }>;  // desk windows
  action?: true;                           // no panel: the icon fires runtime.onAction
  bar?: { commands: { name: string; description: string; arg?: { hint: string; required?: boolean };
                      run: { prompt: string } | { event: true } }[] };
  tools?: { name: string; description: string; input: JSONSchemaObject; effect: "read" | "write" }[];
  contextMenus?: { id: string; title: string; contexts: ("page" | "selection" | "link" | "image" | "window")[]; hosts?: string[] }[];
  commands?: { id: string; title: string; key?: string }[];     // "Cmd+Shift+6"; never overrides an app key
  settings?: ({ key: string; title: string; description?: string } & (
    | { type: "boolean"; default?: boolean } | { type: "string"; default?: string }
    | { type: "number"; default?: number; min?: number; max?: number }
    | { type: "enum"; options: string[]; default?: string } | { type: "secret" }))[];
}
```

Surfaces absent from the manifest do not exist, so the Ledge, the Bar's rows, the menus, Settings and the sheet are all drawn without starting any extension code. The Recorder's:

```json
{ "api": 1, "id": "com.pistachio.recorder", "name": "Recorder", "version": "1.0.0",
  "description": "Record a window, then polish it: zoom that follows your clicks, a smooth cursor, backgrounds, MP4 or GIF.",
  "icon": "icon.svg",
  "permissions": ["capture:tab", "input:events", "media:microphone", "media:camera", "desk", "tabs:read", "files:data", "notifications", "clipboard:write", "notes:write", "power"],
  "worker": { "type": "web", "main": "worker.ts" },
  "panel": { "file": "panel.html", "width": 360 },
  "pages": { "editor": { "file": "editor.html", "title": "Recorder" } },
  "bar": { "commands": [{ "name": "record", "description": "Record the window in use", "run": { "event": true } }] },
  "contextMenus": [{ "id": "record-window", "title": "Record this window", "contexts": ["window"] }],
  "commands": [{ "id": "toggle", "title": "Start or stop recording", "key": "Cmd+Shift+6" }],
  "settings": [{ "key": "fps", "title": "Frame rate", "type": "enum", "options": ["30", "60"], "default": "60" }] }
```

## 4. How it runs

```
            ┌──────────────────── main: the broker ─────────────────────────────┐
            │ ExtensionRegistry · ExtensionScope (grants, Profiles, gesture       │
            │ grants, limits, ledger) · EXT_METHODS · protocol pistachio-ext ·    │
            │ ExtensionViews (pages, panel, worker) · DevWatcher · StatusWriter · │
            │ chrome/ (ECX, store)                                                │
            └───┬───────────────────────┬──────────────────────────┬─────────────┘
   pistachio-ext:call / :event (the extension preload)             │ crx-msg (ECX's own)
                ▼                       ▼                          ▼
   a page: a tab's WebContentsView   the panel: a placed view    Profile sessions
   persist:pistachio-ext-<id>        the worker: a hidden view   (Chrome: service workers,
   (sandboxed, contextIsolated)      (same partition, preload)    popups, content scripts)
          ▲────── runtime.connect(): a MessageChannelMain pair minted by main, main off the path ──────▲
```

**Views.** (A view whose renderer went — a crash, a kill — keeps its identity for the page that comes back, and what its document held goes as on a reload: keep-alives, holds, open writes, subscriptions — `render-process-gone` is a `renewed` to the registry.) Every Pistachio extension context is a sandboxed, context-isolated `WebContentsView` on `persist:pistachio-ext-<id>` (`nodeIntegrationInSubFrames` off: subframes get no preload) with `preload/extension.cjs`. The preload exposes one raw wire and nothing else — `__pistachioWire.call(method, args)` over `ipcRenderer.invoke("pistachio-ext:call", …)` answered by an `ExtReply`, `onEvent` over `ipcRenderer.on("pistachio-ext:event", …)`, JSON and `ArrayBuffer`s only — and runs `runtime.ts` in the page's own world with `contextBridge.executeInMainWorld` before any page script, which builds `globalThis.pistachio` per `pistachio.d.ts` over the wire: `capture.tab` calls `getDisplayMedia` itself, `runtime.connect` wraps a real `MessagePort` (main mints a `MessageChannelMain`, posts one end on the event channel, and the preload hands it to the page's world with `window.postMessage(…, [port])`), `files.data` writes go chunk by chunk. `runtime.ready` resolves once the context knows itself (`runtime.info`); every other member awaits it. Main keeps a map from `webContents.id` to `(extension, context kind)` written when it creates the view, and every handler reads the caller from that map **and** checks `event.senderFrame.url` begins `pistachio-ext://<id>/` (a main-initiated load — ⌘L typed over an extension window, the agent's navigate, back/forward — fires no `will-navigate`, so the view alone is not an identity) with `event.senderFrame === sender.mainFrame` — a message naming an extension names nothing. The preload exposes nothing on any other origin. A navigation of an extension view off its origin opens a new tab beside it instead (main's navigate path, not only `will-navigate`), and its map entry is dropped on `did-start-navigation` elsewhere; an extension opens links with `pistachio.tabs.create`.

**Pages are tabs.** `ui.openPage("editor", { query })` opens a tab at `pistachio-ext://<id>/<file>?<query>` in the current space through `BrowserController` — `kind: "human"` with `extensionId` set, the view made with the extension's partition and preload instead of the tab's, pop-ups denied — and the desk shows it as a window: stills, flights, minimize, ⤢, session restore (device-local: the address is kept for a tab carrying `extensionId`; a restart reopens it; one whose extension is off or gone restores to a placeholder saying so), all as any page's. Its title is the document's; the window's drawer shows the extension's icon and name, so a page never passes itself off as a sign-in. Tidy never archives one, Watchtower never archives one, `pages.read` never reads one, a Chrome extension never sees one (`addTab` skips it), live share never streams one. `singleton` pages are shown instead of opened again. A Profile switch leaves it where it is: it belongs to no Profile's partition.

**The panel.** The Ledge icon's side card: the shell draws the card (the More card's recipe: `setCover`, a press elsewhere or ⎋ closes it, `panel.width` wide, 240–480, default 360) with a head naming the extension and reports its inner slot through a native member (`setExtensionPanelBounds`, the Glance recipe); main places the panel's view there and sizes it by height alone from what the runtime reports (`ui.preferredSize`, a `ResizeObserver` on the document, clamped to the stage; Chromium's preferred-size mode proved unreliable). The view sits in the window's raise order and under the overlay veil, so the shell's sheets, ⌘L and toasts are never beneath it. Closing hides and then destroys the view after a minute; the worker keeps the state. The panel's `before-input-event` relays ⌘ keys to the shell as a tab's does, so ⌘T, ⌘L, ⌘W and ⎋ work while it has focus.

**The web worker.** A `WebContentsView` in a hidden `BaseWindow` (the nub-picture recipe: `getAllWindows()` and the specs are untouched), `backgroundThrottling: false`, loading `pistachio-ext://<id>/__pistachio__/worker.html`, which imports `worker.main`. It starts on first need — a declared event with a handler (a Bar command, a tool call, a menu item, a key, the icon's action), `runtime.sendMessage` from a page, a `capture` or `input` call — and stops after thirty minutes idle with no page or panel open, on memory pressure, or on a crash loop (three in sixty seconds puts it in `error` until the next file change); `runtime.keepAlive(reason)` holds it (the Recorder holds it while recording). Its session's `setDisplayMediaRequestHandler` is what `capture.tab` answers (§5, armed one call at a time, answered only to the worker's frame), its permission handlers answer from the grants (`media` for `media:microphone`/`media:camera`), its `webRequest` refuses everything but `pistachio-ext:` (so `connect-src 'self'` is enforced twice) — which is why `net.fetch` runs in a partition of its own, `persist:pistachio-ext-net-<id>`, through that session's `fetch` — and its proxy is a black hole (`SEALED_PROXY`: `socks5://127.0.0.1:1`, loopback included, since Chromium bypasses a proxy for loopback by itself) with every view of the partition on `disable_non_proxied_udp` (`#sealContents`, on `web-contents-created`, whoever made the view), so what neither the CSP nor `webRequest` sees — WebRTC's STUN and TURN, which would carry anything out as a TURN username — reaches nothing either. MEASURED (Electron 43.4.1): a page whose every request is cancelled still opened a TURN/TCP connection to a server; with the proxy it opened none, nor when loaded without waiting for the proxy to apply (~100 ms); the extensions spec names a TURN server to the panel's `RTCPeerConnection` and hears nothing. A page-world block of `RTCPeerConnection` was not chosen: an `about:blank` iframe has its own.

**The wire** (`packages/extension-api/src/wire.ts`): a call is `{ m: ExtMethod; a: unknown }` answered `{ ok: true; v } | { ok: false; code: ExtErrorCode; message }`; an event is `{ e: ExtEvent; v }` on the event channel; a handler invocation is `{ invoke: { id, kind: "tool" | "bar" | "menu" | "key" | "action" | "message"; name; v } }` on the same channel answered by a `runtime.done` call; `ExtErrorCode = "PERMISSION_DENIED" | "NOT_FOUND" | "INVALID_ARGUMENT" | "UNAVAILABLE" | "TIMEOUT" | "RATE_LIMITED" | "CANCELLED"`. `EXT_METHODS` (`main/extensions/methods.ts`) is `{ "tabs.query": { needs: "tabs:read", input: schema, run: (scope, a) => scope.tabs.query(a) }, … } satisfies Record<ExtMethod, MethodSpec>`: a method in the types without a row does not compile, and a row never reaches `BrowserController` but through the scope. Handlers time out (a tool 30 s, a Bar command 10 s, a menu item 5 s) with `TIMEOUT` written to the status file.

**The protocol.** `pistachio-ext` is registered privileged (`standard, secure, supportFetchAPI, corsEnabled, stream`) in main's one `registerSchemesAsPrivileged` call — which can run once per process, so `crx` (the Chrome library's icon scheme, which the library would register at import) is listed there too and the Chrome libraries are imported lazily after `ready` — and handled on each extension's partition. A bundled extension with dependencies (the Recorder imports mediabunny and gifenc) is built by `apps/desktop/scripts/build-extensions.mjs` (esbuild, `pnpm build` and `dev`) into `out/extensions/<id>/`, which is what the protocol serves and `extraResources` packages; a dev folder is served as it is. It serves the extension's folder read-only with a CSP per response (§6.3), strips types from `.ts` (`node:module`'s `stripTypeScriptTypes`, erasable syntax only), answers `/__pistachio__/worker.html`, and serves `/__data__/<path>` from the extension's data folder with Range support (`<video>` plays an unfinished recording). Chrome's `chrome-extension://` pages are Electron's and untouched.

**Hot reload.** `DevWatcher` watches each dev folder (`fs.watch` recursive, ignoring `.pistachio/`, `node_modules/`, `.git/`, dotfiles; 200 ms debounce so an agent's ten writes are one reload): re-validate the manifest; diff permissions against the grants (widened → `pending`, paused; narrowed → applied); restart the worker; `webContents.reload()` every live page and panel view (the query survives); fire `runtime.onInstalled({ reason: "dev-reload" })`. Every path the loader serves, reads or writes is resolved with `realpath` and refused outside the folder (a symlink to `~` is not a way out).

**Status back to the folder** (`StatusWriter`): `.pistachio/status.json` — `{ id, state, loadedAt, api, manifestErrors, pendingGrants, runtimeErrors: [{ context, message, file, line, at }], surfaces: { bar, tools, pages } }` — rewritten on every change, and `.pistachio/log.ndjson`, console and errors from every context (each view's own `console-message`), 1 MB rotating. With the app closed the file says what it last said; the skill tells the agent to read it after each save.

**Chrome extensions** (`main/extensions/chrome/`, the only folder that imports `electron-chrome-extensions` and `electron-chrome-web-store`). Where a Profile session is configured (`#configureSession`, beside Shields), if any Chrome extension is on in that Profile: `new ElectronChromeExtensions({ session, createTab, selectTab, removeTab, createWindow, removeWindow, assignTabDetails, requestPermissions })`, then `session.extensions.loadExtension(path)` for each. The mapping: one Chrome window, the browser window; `tabs.query({ currentWindow: true })` is the current space's tabs; `createTab` opens a tab in the current space and shows it; `windows.create` opens a tab (a `popup`-type window too: an OS window would leave the desk); `addTab`/`removeTab`/`selectTab` follow `BrowserController`'s tab life, never hidden agent tabs (content scripts still run there: sessions are session-wide; documented). Action state for the Ledge: main asks `browserAction.getState` and folds it into the snapshot (`icon` served by `crx://` through `ElectronChromeExtensions.handleCRXProtocol(defaultSession)`); a click sends `browserAction.activate` with the icon's rect, and the popup is ECX's child window. `getContextMenuItems(wc, params)` is appended to the page's context menu. `chrome.notifications` become notices. The Web Store: `installChromeWebStore({ session, extensionsPath: <userData>/Extensions/chrome, loadExtensions: false, autoUpdate: false, beforeInstall })` per Profile session; `beforeInstall` answers `deny` and hands the id to Pistachio's own flow (§6.5): download, the verdict from the downloaded manifest, the sheet, then `loadExtension`; the same flow from the extensions page and the ⌘L row. Updates run at launch through the registry before any Profile session loads (the library's updater replaces version folders in place); one that widens permissions waits as `pending`.

As built (`chrome/host.ts`, S1): nothing is imported until a Chrome record is on in a Profile whose session shows a page, an install starts, or a tab reaches the store (its page loads once more with the store's preload). main's `prepareSpaceSession` waits up to 4 s for a Profile's extensions to load, so a content script runs on its first page. BrowserController reports the person's tabs through one hook (`chromeTabs`: `added` as a view is made, `selected` in `#activateTab`, `menuItems` for the page menu) ; the host tells the library of a tab only while it shows a web page (`chromeTabUrl`, `#followed` on the tab's first address and each main-frame navigation's start and commit, and the same when the libraries attach to a Profile with tabs already open) — one of Pistachio's own surfaces (notes, a terminal, home), an extension's page or a file is no tab to extensions, and a tab is told of again as it leaves such a surface for the web; the library hears a close through its own `destroyed` listener; a tab removed for such a surface is `tabs.onRemoved` to extensions and `onCreated` again on its return, observed once however often it is told of, and a `webNavigation` event of a tab the library has no tab for goes nowhere (patch hunk 22). An extension never moves the person: `tabs.update({ active })` and `tabs.remove` are the library's bookkeeping only; `tabs.create`/`windows.create` open a tab in the Profile's current space, web addresses only. An unpacked folder that links out of itself — or to nowhere — is refused when added and at every load (`folderLinksOut`): Electron serves the folder whole at `chrome-extension://<id>/`, links followed, and `allowFileAccess: false` keeps `file:` out, not a link (measured). A store install or an approved unpacked folder is on in the Profile in front only (a Chrome extension reaches that Profile's cookie jar). Installs run one at a time (`#oneInstall`): a second asked while the first downloads waits its turn, then displaces the first's sheet and download — never the older finishing last over the newer. The `crx` handler is registered on the default session at launch and forwards to the library once it is loaded: Electron binds a page's protocol handlers when the page commits, so the shell never sees one registered later. The popup is PopupView's, but its size is measured by the glue (`compat.ts` `fitPopup`): Electron 43 never emits `preferred-size-changed` for it, and it would stay 25×25 and hidden; the height is the root element's own box, not `scrollHeight`, which is at least the viewport's and would never let a popup shrink with its content; it opens above the Ledge icon from its leading edge (`"top right"`). On uninstall, `chrome-extension://<id>` storage is cleared in every Profile, plus its `Local/Sync/Managed Extension Settings/<id>` folders (best effort). At launch every Chrome record's folder is read against its grant: a manifest that changed while Pistachio was closed is regranted as a reload would be — widened, it waits paused on its sheet — and a Profile loads nothing whose manifest is not the one approved (the floor under approval, updates and reloads). A click on a Chrome extension's icon with no web page in use — one of Pistachio's own pages or an extension's in front — runs nothing and says so: the library, handed no tab, would take the last web tab it saw for the click, and grant that page by a click made elsewhere. `permissions.request` is granted within the approved sheet alone — a permission or host the manifest declared optional is refused in v1 (no prompt: the extension hears false, as from a person declining), so nothing declared optional widens what a sheet showed. MV3's `chrome.scripting` (`executeScript`, `insertCSS`, `removeCSS`) goes to Electron's own first — the extension's content-script world, `chrome.*` and all — and a call Electron refused for want of a host permission is served by the library instead (patch hunk 23), which knows the grant a click made where Electron's own does not: the tab's `activeTab` grant counts for frames of the page's own origin, every other frame needs a host permission of its own (`allFrames` leaves the rest out, as Chrome does; `frameIds` are each checked), `func`/`args`/`files` run, through the library, in an isolated world of the library's in the top frame (no `chrome.*` there: a script that needs the runtime on a page it reached by the click alone is the one gap; a subframe runs in its page's world, as Electron gives a frame none), CSS reaches the top frame alone, and a trailing callback is taken as Chrome takes one. `activeTab` is kept as Chrome keeps it (patch hunk 21): the tab an action was clicked on, or whose page's menu item of the extension's was chosen, is its to see from then on — the popup's `tabs.query`, a later `tabs.get`, `tabs.onUpdated` — until that tab goes to another origin or closes.

**The status pills, as built** (2026-10-30; `components/extensions/{StatusPills,StatusPillRow}.tsx`, DeskBar, NotchApp). **Capture and input, as built (S3; `main/extensions/{capture,input,keys}.ts`).** *Grants:* `capture.tab`, `capture.hold` and `input.subscribe` take a web page the extension may see (never `pistachio:`, `file:`, another extension's page, a hidden agent tab) that the person granted it — an invocation on that window (a Bar command's tab, a menu item's window, a key's window in use, the icon's), or a pick from `capture.sources()` called by the panel when it is the person's chooser (`panelIsChooser`: the panel open and in view, no veil over it, and opened by the person — the icon, a key, the Bar — or by the worker within a gesture's five seconds; every tab it lists is granted until the panel closes; a panel the worker opened on its own, or anywhere else — the worker, a page — lists the windows but pictures only those granted or recorded, and grants nothing: a chooser no one asked for asks nothing) — or that it records already; a grant lapses when the tab goes to another site, a live capture does not (it follows the window). `capture.tab` works in the worker alone. *The arm:* one request within 10 s from the worker's own frame; the worker partition's permission handler refuses every other display capture (`NotAllowedError`), its display-media handler answers `{ video: tab.mainFrame, audio: tab.mainFrame (asked), enableLocalEcho: true }`; the size asked is the view's × `scale`, at most 3840 on the long side, even px. MEASURED (Electron 43.4.1): the worker's partition capturing a Profile partition's tab asks nothing of the tab's session, needs no gesture and no macOS permission, starts in 100–116 ms, 56–61 fps, follows navigations and ends with the page; a fresh sink on a static page gets a frame in ~4 ms. *Live:* each second main asks the worker's page how many display tracks it holds live (`__pistachioLiveCaptures`, the guard the extension preload sets in the page's world before its first script — see *Ending*; a count no script of the page can fake) and reads the tab's `webContents.isBeingCaptured()` (Chromium's count of every capturer there is — a live share's, Playwright's under e2e, where every page reports captured — so it can say a capture is over, never that this one runs), and ends a capture whose worker holds no track (after a 3 s start grace: the stream is a few ms behind its answer) or whose page reports no capturer, whose tab closed or woke as another page, went to an address no extension records, or left the extension's Profiles — the worker hears `capture.ended` and its runtime ends the tracks; the extension's last `capture.release` on the tab ends its capture too. (The count is per worker: with two tabs captured at once, one stopped is seen as over when the other is.) *Ending:* a capture told to end — the person's Stop, an address capture may not see, its last hold released — stays listed (the pill up, the tab held) until its worker holds no live track; one still held 3 s later has its tracks ended by main itself (`CaptureBook` `enforce` "end": the extension preload wraps `getDisplayMedia` and `MediaStreamTrack.clone` in the worker's world before its first script and keeps `__pistachioLiveCaptures` and `__pistachioEndCaptures`, globals no script can replace, that list every live track by its source (Chromium names a tab capture's source in the track's `deviceId`, `web-contents-media-stream://<process>:<frame>` of the source's main frame; main spells the same from the frame at the answer) and stop one source's tracks — another capture of the worker's untouched — called with the intrinsics saved at install, never a prototype the page may have changed — the list of sources is made of own properties by `Object.defineProperty`, since a setter put on `Array.prototype` would swallow an assignment; and main reaches the two not through the page's globals, which a script may rebind (`globalThis = {…}`), but in the preload's isolated world, which keeps the functions as `executeInMainWorld` handed them back (`EXT_GUARD_KEY`, asked with `executeJavaScriptInIsolatedWorld(999)`; a page with no guard there answers nothing, taken as holding), with a warning in its log; one still held 3 s after that, or whose worker gives no answer within a second (hung), has its worker's renderer killed (`enforce` "kill"), with an error. The runtime told is the extension's own code, and a stream taken with the raw wire is in no map of its, so the person's Stop rests on main, never on the extension. The guard is one realm's: a subframe of the worker's document — an `about:blank` one, the only kind its CSP leaves — has intrinsics of its own, and a track cloned through its `MediaStreamTrack.prototype.clone` is one the guard never counts (MEASURED, Electron 43: such a clone stays live past the original's stop; a Web Worker cannot be handed a track at all — not transferable). So a worker page that ever makes a subframe (`frame-created`, `ViewIdentity.framed`, for the life of that contents, a reload included) has its word discounted: `liveTracks` answers null for it — taken as holding — the pill stays up, and a capture told to end goes the "kill" way, which no realm survives; the log says so at the frame. MEASURED (Electron 43.4.1, 2026-11-02): a tab capture whose page is closed, or whose renderer is killed, stays counted on the captured tab for that tab's life — `isBeingCaptured()` never drops, not after 16 s, a reload or a navigation — and under Playwright every page reports captured from the start; which is why the count never says a capture runs, and ending the tracks is the one clean way. Held and captured tabs are never slept, archived or reset by Tidy, nor zoomed for the desk (100% while held), and are woken and laid out while hidden. *The pill:* while an extension captures or watches input, `captures` lists the tabs and the pill is main's (`● Recording · <name>`, Stop) — or the extension's own with a leading ● and a Stop added when it has none; main's own Stop ends the captures and subscriptions after the extension's handler answers (or 3 s). *Input:* `t` is main's `performance.timeOrigin + performance.now()`; batches every 50 ms (a press waits ≤ 100 ms for its element); coordinates in the view's DIP; a frame of another site is placed by matching its press to main's (or to the OS pointer: an out-of-process frame's presses never reach main's `before-mouse-event`); while any frame says a secret field (password, `cc-*`, one-time code) has focus, no key and no caret goes out — focus is read from the document, into open shadow trees (a move inside one fires past no root, so each tree focus enters — or sits in as the watch begins — is listened to from inside, until the watch ends), and a focused element that is not one focused for itself — a custom element, a div, a span: any but the natively focusable kinds — is taken as a host hiding a closed tree, and secret, since what has focus inside it cannot be seen (a custom widget focused by tabindex is silenced the same: safety over its chords); the subscription opens with the view's `box`, the page's `nav` and `load`. *Keys:* `Cmd`/`Ctrl` → `Mod`; a key the person's shortcuts, the editing keys, the menu's or the Mac's hold — or an extension earlier in the order — stays unbound, and `status.json` `keys` says why; the app's own binding wins at the moment of the key.

## 6. Security

### 6.1 Capabilities, tiers, the sheet's words

| Tier | Capabilities | The sheet says |
| --- | --- | --- |
| Low (one line) | declared surfaces, `storage`, `notifications`, `clipboard:write`, `power`, a gesture grant | "Adds /prs to the Bar." |
| Medium | `tabs:read`, `tabs:write`, `desk`, `notes:read`, `files:data`, `hosts` (named) | "Sees the titles and addresses of your tabs." "Talks to api.github.com." |
| High (named one by one) | `pages:read` + hosts, `capture:tab`, `input:events`, `media:microphone`, `media:camera`, `notes:write`, `agent:tools`, `agent:ask`, `clipboard:read` | "Can read pages on github.com." "Can record a window you choose, and what you click and type in it (never your passwords)." "Can use the microphone." "The agent can call it and send it what it reads." |
| Critical (red, a second confirm) | `hosts: <all_urls>`, and later `node`, `node:fs`, `node:exec`, `terminal:run` | "Runs programs on your Mac with your access. Pistachio can't limit what it sends." |

**Gesture grants.** Invoking an extension on a tab — its Bar command, menu item, key, or panel opened from that tab's window — grants `pages:read` on that tab until it navigates to another site. Most agent-written extensions need no host grant; the skill teaches this first.

### 6.2 Never silently

- **Other Profiles.** An extension is on per Profile (`profiles: "all" | ids`). `ExtensionScope` filters every result and event to the Profiles where it is on; capture refuses a tab elsewhere; hidden agent tabs (`hiddenFor`) are never listed.
- **Site sessions.** No cookie API. `net.fetch` runs in `persist:pistachio-ext-<id>`, never a Profile's partition. The only way to a signed-in page is `pages.read` on a tab the person has open, gated as above.
- **Exfiltration.** Extension pages have no direct network (`connect-src 'self'`); every byte out goes through `net.fetch`, host-checked, written to the ledger (`<userData>/ExtensionData/<id>/ledger.ndjson`, shown on the page as "Sent to api.github.com: 41 requests today").
- **The shell's IPC.** An extension context's preload exposes two channels of its own and no `ipcRenderer`; the shell's 200-odd `pistachio:*` handlers are unreachable from it by construction. Defence in depth, before any extension work: a central guard in main refuses every `pistachio:*` IPC whose sender is the shell but whose `senderFrame` is not the shell's main frame (`main/ipc-gate.ts`, installed before `installIpc()`, with a unit test), and an e2e that an extension page finds no `require`, no `ipcRenderer`, and a `pistachio` with only the API's members.
- **Approving.** Nothing enables itself. A folder that appears raises a notice (*New extension: GitHub inbox · Review*). A library entry's *Turn on* loads it waiting on the person, and its sheet comes up at once (2026-10-30, `turnOnFromLibrary`: once a snapshot shows it pending, with no notice beside it) — the person asked for it, and should not have to find *Review*. A reload that widens pauses until approved; the approval names the `manifestHash` the sheet showed. The agent's drafts land paused, and the agent's later writes to an approved folder land paused too (a tree hash beside `manifestHash`; the sheet says *Pistachio changed it* with *View changes*): a person's own edits hot-reload, an agent's never run unseen. The agent has no `install` or `approve` tool. Ids `com.pistachio.*` are the library's; a record is bound to (id, source), and a second folder claiming a known id is refused with a status line saying why — it would otherwise inherit the grants, the partition and the data.
- **Agent tools** exist in a turn only when the extension is on in that Profile, holds `agent:tools`, and the person left *Agent can use it* on; they form the `extensions` tool group a policy can turn off; the model-facing name is `x_<six hex of the id>_<tool>` (descriptions capped at 400 characters, prefixed with the extension's name); inputs are written to the ledger; results reach the model framed as untrusted extension output, as page text is; a tool declared `effect: "write"` is listed on the sheet as such (the approval card per call is later).
- **Spending.** `agent:ask` is High, rate-limited, counted in the AI usage under the extension's name.

### 6.3 CSP and the frame

Per response from the protocol handler: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; media-src 'self' blob: mediastream:; font-src 'self' data:; connect-src 'self'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`. No remote script: the code on disk is the code that runs. The shell's CSP allows `img-src pistachio-ext: crx:` for icons and nothing more. An extension's view always sits inside chrome that names it (the panel card's head, the window's drawer with the extension's icon and name), and approval sheets, permission UI and password prompts are never drawn where a view could cover them (the panel view is under the overlay veil).

### 6.4 Chrome extensions: the verdict

Read from the **downloaded** manifest before anything loads (`chrome/verdict.ts`, pure, tested) — never from the manifest the store's page sent: **✕ won't work** when its core is an API Electron lacks or Pistachio keeps for itself — a blocker built on `declarativeNetRequest` (DNR itself was measured to block a request on Electron 43, but Shields is the blocker here: "Shields already blocks ads and trackers here"), MV2 blocking `webRequest` (Shields' hub pre-empts it), `sidePanel` as its only surface, `identity` with an `oauth2` block (Chrome's Google sign-in), `userScripts` (Tampermonkey), `tabCapture`/`desktopCapture`, `debugger`; **◐ partly** when something it uses is missing but not its core (`omnibox`, `bookmarks`, `history`, `downloads`, `tabGroups`, `commands` beyond `_execute_action`, `nativeMessaging` until verified), each named in words; **✓ works** otherwise (`offscreen` documents and `alarms` were measured to work; `runtime.onInstalled` never fires on a load, so an extension that only builds its menus there builds them late). A compatibility index for the most-installed hundred (`id → verdict, note`), kept in the repo and refreshed later from our server, overrides the static read: measured beats inferred. Password managers (native messaging to a desktop app, which checks the browser's signature) are the P0 set to verify by hand; until verified the verdict says ◐ honestly: "signing in works; unlocking with the desktop app isn't available in Pistachio yet".

### 6.5 The libraries, as shipped and as patched

Read in full (2026-10-30), `electron-chrome-extensions` 4.10.0 and `electron-chrome-web-store` 0.13.0 are starter code, not a boundary. Pinned exactly and patched through pnpm (`patches/`), each patch a few lines named here so an upgrade re-applies them knowingly:

- The router takes the extension id **from the renderer** (`crx-msg`'s and `crx-add-listener`'s first argument): patched to derive it from `event.senderFrame.origin` (`chrome-extension://<id>`) or the service worker's scope and refuse a mismatch — otherwise a compromised page renderer names any extension and reads its Profile's cookie jar. `crx-msg-remote`, which let any renderer name any partition, is dropped: main calls the action API in-process.
- `chrome.cookies` is injected into every extension with **no permission and no host check**: patched to need `cookies` and to filter `get`/`getAll`/`set`/`remove`/`onChanged` by the extension's host permissions, as Chrome does.
- `tabs.update` navigates from main (`loadURL`) around every `will-navigate` guard — to `pistachio://terminal/<id>`, `file:`, `data:`: patched to go through an `impl.navigateTab(tab, url)` hook that `BrowserController` answers with its own guards.
- `insertCSS`, `tabs.*` details and `webNavigation` events have no host check: `insertCSS` patched to need a host grant; tab URLs and titles are given only with `tabs` or a host grant for that URL. Pistachio's own addresses (`pistachio:`, `pistachio-app:`, `pistachio-ext:`, `file:`), hidden agent tabs, Glance, sign-in pop-ups and every app surface are never `addTab`'d.
- The Web Store's origin check is a prefix match (`startsWith("https://chromewebstore.google.com")`): patched to an exact origin, and `management.uninstall` from a page dropped.
- The store's own install path shows the page's manifest and loads after download with no second look: Pistachio installs by id itself (`downloadExtension`, then the verdict and the sheet from the downloaded manifest, then `loadExtension`), and the page's *Add to Chrome* only hands over the id (`beforeInstall` answers `deny` and starts our flow). `loadExtensions: false`: only the registry decides what loads. `autoUpdate: false`: updates run on launch through the registry, which compares the new manifest to the grants and pauses one that widened.
- Patched in the compiled `esm` and `cjs` builds both (main runs the `.mjs`); per-extension redaction of tab details, `webNavigation` and `cookies.onChanged` is partial where the library broadcasts (`router.broadcastEvent`), listed in `patches/README.md`.
- Not patched in v1, stated: CRX signatures are not verified (integrity rests on TLS to Google); native messaging's framing is wrong for non-ASCII and a hostile host can throw in main (password managers are ◐ until rewritten); the frame preload evaluates in every tab frame (inert off `chrome-extension:`); the five-hourly update check tells Google the installed ids (disclosed in Settings).

## 7. Install, update, directories

| What | Where |
| --- | --- |
| Registry | `<userData>/extensions.json`, atomic, main the only writer |
| First-party | `Resources/extensions/<id>/` (`apps/desktop/extensions/<id>/` in dev) |
| Chrome (store) | `<userData>/Extensions/chrome/<cwsId>/<version>/` |
| Data | `<userData>/ExtensionData/<id>/` — `storage.json`, `data/`, `ledger.ndjson`; removed on uninstall after a confirmation |
| Dev | `~/Pistachio/Extensions/<folder>/` (not `~/Documents`: iCloud placeholders break watchers and git), plus folders added with *Load a folder…* |

```ts
interface ExtensionRecord {
  id: string; kind: "pistachio" | "chrome";
  source: { type: "bundled" } | { type: "dev"; path: string } | { type: "webstore"; cwsId: string; version: string } | { type: "unpacked"; path: string };
  enabled: boolean; profiles: "all" | string[];
  grants: { capabilities: Capability[]; hosts: string[]; manifestHash: string; at: number } | null;   // null: never approved
  pending: { manifestHash: string; widened: Capability[]; hosts: string[] } | null;
  pinned: boolean; order: number; agentAllowed: boolean;
  installedAt: number; updatedAt: number;
}
```

`api: 1`; the app loads `api` N and N−1 and refuses the rest with a status line. First-party updates with the app, grants carried over unless widened. Uninstall clears the extension's partitions and data after a confirmation. One partition, storage and worker per extension across the Profiles it is on in (v1; a Profile boundary inside an extension is later). A call with no tab acts in the Profile in front; a worker invocation carries the Profile of the context that invoked it. Sync of the installed list (sealed records, arriving paused on another Mac) is later.

## 8. The agent as an author

`/extension <wish>` (group *Make*; also what routing picks for "make me an extension…" typed to the Bar; it turns Developer mode on with a notice if it was off) runs an **author turn**: the `extension_author` tools — `extension_draft_write(slug, path, content)`, `extension_draft_read(slug, path?)`, `extension_status(slug)` (the status file, so the agent sees its own load errors and fixes them) — are registered in that turn alone (never in the default tool groups), reach only `~/Pistachio/Extensions/<slug>/` (≤ 256 KB a file, never `.pistachio/**`, no symlinks, a manifest naming `<all_urls>` refused), and the turn carries no page, mail or notes tools: an extension is never written by a turn that read untrusted content. The agent's rules carry the API's `AGENTS.md`. The folder lands paused; the Bar's answer card shows the approval sheet in its compact form with *View code* (the files in a desk document window). Every later change is the same path: `@<name>` in the Bar mentions it, "also hide the Shorts tab" is a new draft that lands paused with *View changes*, approval applies it, and ⌃Z's five seconds undo it (the folder keeps `.pistachio/versions/` as plain copies; git is the person's).

As built (S5): `draftFolder` answers the folder with `author: { slug, token }` (128 random bits, claimable once, this session); the Bar's prompt starts with `[pistachio:extension-author slug=<slug> token=<token>]`, which `RunController` reads and strips (`#authorMarker`) — a marker whose token main never handed out (an extension's `agent.ask`, a pasted line) is dropped and the message is ordinary. A claimed marker starts a **thread of its own** (`#startFresh`: nothing a page, a mail or a note said is in its history) whose turns — and the turns that continue them (an answer, a resume, a word while it runs) — run with `AiAgentRunInput.author`: the three tools plus `ask_user`/`ask_user_text`, nothing else (no takeover, no `task_notes`, no memory, desk, extension tools), its prompt the frame plus `AGENTS.md`, one call of 40 steps and no checkpoint; a follow-up after it ended is an ordinary turn. The draft tools also refuse dot-files and `node_modules/` (the watcher ignores them, so they would never reload) and write through a temp file renamed into place (a link put there is replaced, never followed). A draft that does not load yet is not registered (its status file says why), so the Ledge and the *New extension* notice see it only once it loads; while the turn writes, its Ledge icon breathes (`ExtensionInfo.drafting`) and the sheet refuses approval, and an approval is refused too while what the agent last wrote has not been reloaded. A write to an approved folder sets `pending.changedBy = "agent"` before the file lands (`markAgentChanged`), which every reload keeps until the person approves again (the sheet: *Pistachio changed it*). Not built: the compact sheet in the answer card, *View code* / *View changes*, `.pistachio/versions/`, ⌃Z, `@<name>` edits, the tree hash, a shimmering slot before the folder first loads, routing "make me an extension…" here.

## 9. The Recorder

`apps/desktop/extensions/recorder/`, `com.pistachio.recorder`, a `web` worker, a panel, an editor page. Measured on Electron 43.4.1 (M4, 2026-10-30): tab capture through `getDisplayMedia` answered by the host's display-media handler with the tab's main frame starts in 133 ms and delivers 58 fps with no macOS permission; asking for twice the view's size makes the page render at device-pixel-ratio 2 so zoom stays crisp on a 1× display; page audio comes in stereo with `enableLocalEcho` when echo cancellation, noise suppression and gain control are off; H.264 and HEVC encode in hardware to 4K60, AAC and Opus encode; a 1080p60 decode → compose → encode export runs at 203 fps (a two-minute recording in about 40 s). Chromium draws the system cursor into a tab capture whenever the mouse moves over the page and ignores `cursor: "never"`: v1 draws its cursor exactly over Chromium's ("Natural"; ripples, size and zoom work, smoothing waits for a native hook that hides the cursor from the capture).

**Record.** `/record`, the Ledge icon (the panel: source — the window in use, or any desk window with its still —, mic, camera, *Start*), *Record this window* on a window's ⋯, or ⌘⇧6; a count of three in the status pill, never over the page. The worker holds the tab (`capture.hold`), takes `capture.tab(tabId, { audio: true, scale: 2 })` and `input.subscribe(tabId, […])`, encodes with mediabunny (`MediaStreamVideoTrackSource`, H.264 High, a keyframe a second, fragmented MP4 through a `StreamTarget` into `files.data.write("rec/<id>/screen.mp4", …)`; the mic to `mic.m4a`, the camera to `camera.mp4`), and appends events to `events.jsonl` in 250 ms batches — a crash loses a second. The status pill shows the time, the mic level, pause and stop; the recorded window wears a red ring in the agent ring's slot; ⎋ never stops a recording. The recordings root is `~/Movies/Pistachio/`, a folder per recording (the tracks, `events.jsonl`, `edits.json`, a thumbnail), listed in the panel's *Recent*.

**Edit.** `ui.openPage("editor", { query: "rec=<id>" })` opens the editor as a desk window (the desk's layout model places it, as any new window). One deterministic `render(tOut)` on Canvas2D/WebGL draws the frame: the raw video (seeked, decoded with WebCodecs) on a background (gradients, the space's colour, wallpapers, a solid), padding, radius, shadow; the camera from zoom segments derived from the events (a click zooms to the clicked element's rect plus padding; typing holds on the focused field or the caret; scrolling pans; nearby segments merge; a critically damped spring moves the camera and looks ahead by one segment); the cursor redrawn from `move` events in Natural mode (a vector set keyed by `cursor` shape, click ripples, hidden when still); speed ramps (idle over 1.5 s runs ×4 with a ⏩ chip, typing ×2, never while the mic hears speech) as a time map. The inspector (280px, trailing): Background · Frame · Cursor · Zoom · Speed · Audio. The timeline: clips, zoom segments (draggable edges; Z adds one at the playhead), speed segments, event markers (clicks, navigations as chapters). Keys: Space, J/K/L, I/O, ⌘B split, ⌫, ⌘Z.

**Export.** MP4 (H.264, 1080p or the source size, 30 or 60), WebM (VP9), GIF (gifenc, in a Worker, 3–7 ms a frame measured) — the export runs `render` in a Worker over a `VideoSampleSink` → `CanvasSource` → `Output`, with an ETA in the button; the result goes to the screenshots folder (`screenshotFolder()`, as ⌘⇧1's do) and a notice says *Exported · Show in Finder · Copy*. The finished card offers *Copy*, *Reveal*, *Add to a note* (a link, until notes have a video block), and drag-out to the Finder.

**Not in v1**: the whole Pistachio window or the screen (a native ScreenCaptureKit module with the cursor off, later), the desk as a scene (every window a track), captions, redaction by meaning, *Turn into a guide*, recording a live share.

## 12. Not done / open questions

- **Keyboard over an extension view.** A page's view is a tab's, with the tab's ⌘-key relay; the panel's view gets the same relay. (A spike of the iframe design found `before-input-event` fires on the shell for keys typed into a focused cross-origin frame while the shell's own `keydown` never sees them — moot now, kept for the record in the scratchpad.)
- **The app's own hardening** is prior work the risk pass flagged: no Electron fuses are flipped and the entitlements allow `DYLD` variables, so a local process can already borrow Pistachio's camera and microphone grants; fix before Pistachio ever holds a Screen Recording grant.
- **Content scripts run in the agent's hidden tabs** (they are the Profile's own partition, and Electron injects per session); disclosed, not fixed; a shadow partition for hidden tabs is later.
- **Chrome, S1 gaps.** `tabs.query({ currentWindow: true })` is the Profile's every listed tab, not the current space's: the library ignores `currentWindow` and caches tab details (`assignTabDetails` could not follow a space change); `{ active: true }` is the tab in use. `permissions.request` is granted without a sheet (already narrowed to what the manifest declared). `chrome.notifications` become one-line notices: their click and close are not wired back. An extension's own page asked for as a tab (an options or welcome page, `chrome-extension://`) is refused. Extensions cannot switch or close tabs (a tab manager is ◐). An unpacked Chrome folder is not watched: *Reload* reads it again.
- **Capture, S3 gaps.** The shell draws no ring on a captured window yet (main lists it in `captures` and shows the pill). Extension key commands work but are not listed in Settings → Keyboard (a collision leaves the key unbound and `status.json` names the holder). A folder copied into the dev folder can fire a dev-reload about a second later (macOS file events from the copy), which restarts the worker: a spec waits 1.5 s after copying.
- **The author turn, S5 gaps.** The approval sheet in its compact form inside the answer card, *View code* / *View changes*, versions and ⌃Z, the shimmering slot while the folder is first written, and routing a plain "make me an extension…" to the author turn are not built: `/extension <wish>` is the way in. The router's prompt carries extension tool descriptions, which are the extension's own text.
- **Shields Strict** strips cross-site cookies from an extension service worker's calls to its own service; treating `chrome-extension://` requests as first-party for hosts the extension holds a grant on is the likely answer, undecided.
- **P1, every Electron upgrade**: an extension in Profile A calling `scripting.executeScript` on Profile B's tab ids, the overlay views (`file://` in a packaged build) and the shell must be refused; a CI probe to keep.
- **A handler's Profile after an await.** Main binds a worker's calls to the Profile of the invocation in hand; once a handler has awaited, its later calls cannot be told from another invocation's, so with invocations from two Profiles in flight (a command awaiting the network while the person switched Profiles and ran another) a call that names no space acts in the Profile in front when it is one of them (`ExtensionScope.callProfile`). A handler that must act where it was invoked names its space (`tabs.create`'s `space`, `ui.openPage`'s, from its context's `spaceId`) — a space named is its Profile named. Per-call binding would need the runtime to tag calls by handler, which the page's world cannot do across awaits.
- **The cursor in tab capture** (§9): the native hook (`+[NSCursor currentCursor]` returning a transparent cursor while a tab recording is live) is unprobed with the screen unlocked.
- **HiDPI capture lingers**: the page's device-pixel ratio stays 2 for a while after a 2× capture stops (measured 800 ms); start captures inside the countdown so the swap is never recorded; offer *Native resolution*.
- **Password managers.** 1Password and Bitwarden depend on native messaging; the web-store library runs Chrome's `NativeMessagingHosts`, unverified here.
- **`node` workers** are the power an agent-written tool wants most (CLIs, project folders, sqlite) and the Critical tier; Node's permission model under `utilityProcess` works only through `NODE_OPTIONS` (spiked), is a seat belt not a sandbox, and dies if the `nodeOptions` fuse is ever turned off.
- **Write-effect tools** pause for the person per call: not built; the sheet names them.
- **Sync** of the installed list, **sharing** a folder as a link or a `.pistachio` file, **Remix**, *Ask Pistachio what it does* on a shared one: later.
- **Per-space scope** ("only in these spaces"): the most Pistachio-ish idea and the easiest to over-build; the record has `profiles`, not spaces.
- `chrome.commands` beyond `_execute_action`, `omnibox`, `tabGroups` as spaces, options pages as a Glance: later.
- A manifest key is written `Cmd+Shift+6` (an author's words); main maps it to the app's `Mod+` form. An extension's `/` command whose name a built-in (or an earlier extension's row) holds (`/share`, `/summarize`) is listed and completed as `/<extension's last id segment>-<name>` instead (the first eight letters of a Chrome extension's id), and still runs the command it declared.
- *Build with Claude Code* always starts in a new draft folder of the dev folder (named for the wish, or `my-extension` with none), which turns Developer mode on and lays `AGENTS.md` and the skill there — never in a fallback directory. It passes the wish as an argument, never interpolated into a shell line: the terminal's `open` carries `run: { program: "claude", args: [wish] }`, and the host starts the login shell with `exec "$0" "$@"` and those after it (docs/terminal.md).
