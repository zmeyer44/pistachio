# Security model

## Properties

- Forked authority: the human session remains available; the task receives a separate partition and capsule.
- Bounded reach: origin, method, transfer, interaction, sensitive-page, and semantic-action classifications are derived and enforced at the delegated session's request boundary.
- Credential separation: cookies and captured page context share an authenticated-encryption envelope in broker/main-process memory and are hydrated directly into a target session. Password and hidden controls are excluded at capture. The sealed values are not part of renderer IPC or agent prompts.
- Independent revocation: terminal states destroy the capsule key and cut task egress. Deleting a key does not invalidate arbitrary third-party server sessions, so network cutoff is the enforceable revocation fact.
- External policy: the model cannot approve its own action. Consequential actions require a held request and an exact one-use capability.
- Durable human pauses: approval, judgment, and step-up are run states with leased, idempotent, bounded-attempt delivery—not a blocked model call. Expiry actively revokes the run.
- End-to-end-encrypted sync: cookies, workspace docs, and cloud-run content are sealed on devices under per-Space root secrets that only devices hold (password, recovery-code, and sender-signed device-to-device wrappers). The control plane and hub see pseudonymous record ids, sizes, and timing.
- Credential vault: values a person hands to a cloud run and chooses to keep are sealed under the Space seal key by the cloud device (or by the person's own browser or Mac when added by hand) and stored on control as ciphertext with field names only. A later run opens an entry on the cloud device and types it straight into preflighted, origin-bound controls; the model learns only that the fields were filled. One-time codes are never kept, a value the site rejects is not retried within a run, and the person can read, edit, and remove every entry from Settings → Vault.
- Dedicated integrations: a service the agent reaches through its API (Gmail, Google Calendar) is connected with an OAuth grant the person makes on their Mac, at an access level that fixes both the scopes asked for and the tools the model is given. The refresh token is sealed under the Space seal key before it leaves the device and stored on control as ciphertext with the provider, account, and level in the clear; each executor mints access tokens in memory for one run and never stores them, and the model sees only the account's name and level. Disconnecting from a device that holds the Space key revokes the grant at the provider before the row is deleted; from one that does not (a web app) it leaves a tombstone no executor binds, that a run already holding the grant notices within 30 seconds, and that the next key-holding device revokes. A grant the provider revokes is flagged for reconnection. See [integrations](integrations.md).
- One writer per session: origin leases arbitrate between a person's devices and the cloud browser; the cloud browser's leases are exclusive and renewed only while a run is active.
- Streamed chrome, not a hosted page: the browser app (`apps/web`, its own site) holds exactly the keys it already held — its own enrolled device key pair, and the Space keys derived in tab memory during an unlock (kept for up to 30 days in this browser's IndexedDB if, and only if, the person chose "stay unlocked": see the key-retention non-claim below) — and receives from the session's host only what chrome needs. Outward, that is pixels (JPEG frames of the visible panes), snapshot metadata (tab titles, URLs, favicons, split and shelf state), conversation content the host opened under the Space key it is already driving the session with, and the four things S6 added because the person is here and the page is not: text the page put on its own clipboard, what the pointer was over on a right-click (the selection, the link, the image address), a reader tab's article as the `data:` document its address is (shown to the viewer whose tab it is, and deliberately never written to the synced record), and a download's bytes over the session's own HTTP route. Inward it carries the viewer's forwarded input, up to 32 MiB of files the person picked in their own browser, text from the person's clipboard when they paste, and — only after they answer a prompt for that site — the position their own browser reports. Cookie material, storage, and the page's own HTML never leave the worker, and a site is never embedded in an iframe, so nothing on the page's origin can reach them either. Control keeps storing only sealed records.
- Layered admission to a session: a shell socket upgrade is refused unless its `Origin` is the browser app's exact origin (`PISTACHIO_BROWSER_URL`, one origin and not the dashboard's) when the upgrade carries one — which a browser always does, and which is what makes this a boundary for pages: a page elsewhere cannot drive someone's browser whatever it holds, and a client that sends no `Origin` is not a page and still has to spend a ticket. The credential in the URL is a one-minute, one-redemption `pst_` ticket — no WebSocket client can set a header — spent at control with a single delete that is itself the authentication; it is not a bearer for any other route and cannot be replayed onto another session. A fresh ticket is minted for every dial, reconnects included. After accept the host sends a nonce challenge and nothing else until the viewer answers with a proof sealed under the Space key, so an enrolled device of the owner that cannot open the Space cannot watch it either. The viewer's device is re-checked every minute and a revoked one is closed.
- Fenced handovers: a browser session carries a control generation alongside its holder. A run starting, a person taking control, and a release each bump it in control's own transaction, and every forwarded input and every agent tool call carries the generation it was issued under — the tool call's stamp is re-checked immediately before the Playwright call, after every await the dispatch went through, so an action already in flight when the person took over is refused rather than performed. The host drops anything older and counts the drop, so a takeover is a fence rather than a race, and a released agent cannot land a keystroke behind the person's. The members that act for the person and mutate the page (paste, upload, print) are refused while the agent holds control: they are forwarded input by another name.
- Session authority is a lease, not a device token: control refuses a `cloud` device every device-bearer route, so the worker holding a person's session cannot impersonate them to start or steer a run. The console's routes are internal ones authenticated by the service bearer together with the session's lease token, scoped to that session's own runs, with the viewer's device id as the audit actor — which control verifies is an unrevoked device of the session's own user, so a worker cannot invent who acted. The lease travels in a header (`x-pistachio-session-lease`) and is compared in constant time, and control's request logger scrubs it: it authorises acting as the person in their own Space, and control logs every request's query string.
- Attributed evidence: every record includes the agent, human sponsor, task, purpose context, previous hash, signer, hash, and signature; verification accepts an external root/length anchor.

## Trust boundaries

Trusted: native main process, hosted control (for identity, ordering, and leases, not for session contents), credential broker, enforcement proxy/CDP guard, runtime supervisor, evidence signer, and the cloud browser runner for Spaces the person has explicitly enabled for cloud runs.

Untrusted: model output, agent harness plugins, page content, prompt text from pages, SaaS responses, notification links, and the renderer beyond its narrow IPC schema.

The web page is chrome, not a plane. It is trusted with what it already holds — its enrolled device identity and the Space keys it derives in tab memory — and with nothing else: it drives a session only through calls the host validates per method and input the host fences by generation, and a member the host does not implement is refused rather than approximated. What arrives from a session is untrusted in exactly the way a native tab's content is: a frame is a picture the page painted, and a snapshot's titles and URLs are strings a site chose.

The current demonstration uses an in-process scripted agent and local partitions. It validates UI, capsule isolation, Electron request-boundary enforcement, popup/navigation containment, takeover, revocation ordering, and evidence contracts. It does not yet validate cloud sandbox isolation, proxy-level exfiltration resistance, laptop-close continuity, WebAuthn step-up, or KMS-backed signer identity.

## Non-claims

- Pistachio cannot force logout on arbitrary SaaS applications.
- A page-readable bearer token cannot be made HttpOnly retroactively; adapters should prefer delegated OAuth/service credentials where available.
- Origin allowlists alone do not prevent data exfiltration to an allowed origin; endpoint, method, payload/DLP, and semantic controls remain necessary.
- Hash chains reveal tampering but are only externally trustworthy when the signing public key is anchored outside the bundle.
- The native client currently has the Electron storage-fidelity gaps listed in the reuse ledger. Unsupported capture must fail closed.
- The OAuth client an integration uses is an installed-app client whose secret the provider does not treat as confidential; control hands it to enrolled devices so both the Mac and the cloud device can refresh tokens. Anyone holding that client cannot open a grant — the refresh token is what confers access, and it is sealed — but can start a consent flow branded as Pistachio.
- Enabling the cloud browser for a Space gives the runner that Space's root secret; a compromised runner can act as the person in those sessions. The control plane introduces the runner's public key on first enable; the desktop pins it afterwards and shows fingerprints, which makes later substitution visible but does not prevent a first-enable substitution.
- A shared static egress IP reduces but does not eliminate re-authentication: sites that bind sessions to device fingerprints will still challenge the cloud browser.
- Revoking a device stops future Pistachio access and cuts its egress and hub sockets; it cannot invalidate third-party sessions already copied to that device.
- Some capabilities are deliberately unavailable in a web tab and are declared rather than approximated: passkeys and WebAuthn (an assertion binds to the origin of the browser making it, which is the browser app's, not the site's), camera and microphone inside a site (the media would have to travel from the viewer's machine into a cloud page), importing from browsers installed locally (the desktop does that; sync carries the result), auto-update, and shortcuts the viewer's own browser or OS reserves. The shell shows these as unavailable; it does not fail silently.
- A download's bytes leave the worker over HTTP, not over the shell socket, so they carry the socket's kind of credential rather than a device token. The URL is not the whole credential, precisely because a download URL is handed to the person's browser and ends up in its history, its extensions, and every proxy in between: the token in it is good for one download and sixty seconds, and the request must also present the viewer's own download key, which the host issued to that one socket after it proved the Space and which travels in the `x-pistachio-download-key` header rather than in the address. Because a header is not something `window.open` can set, the page fetches the route, and the route therefore answers the CORS preflight — for the browser app's exact origin and never `*`, so a page elsewhere holding a URL it had somehow got hold of still cannot read the bytes — and pins `Origin` on the request itself. It relays inside the fleet to the worker holding the session, as the socket upgrade does, so the fleet's one public address does not make a download a coin flip.
- Keys can outlive the tab, by choice, behind a PIN. By default the Space keys a web app derives at unlock live in that tab's memory and a reload asks for the password again. "Stay unlocked" trades that away: after the password has worked, the person chooses a six-digit PIN, and this browser's IndexedDB keeps the Space root secrets sealed under a key derived from it (PBKDF2-SHA-256, 600,000 iterations, one derivation per record) for 30 days. Coming back is the PIN, not the password. **What that is and is not worth:** six digits is a million possibilities, so someone who copies this browser profile can grind the sealed blob offline — the KDF makes that expensive, not impossible, and it is the honest limit of a PIN with no secure element behind it. What the PIN does buy is that nothing usable is at rest and nothing opens without a challenge, which is strictly more than the previous design (non-extractable key handles, usable by anything that opened the origin, with no challenge at all). Five wrong tries destroy the record; the count lives inside it, so it survives a reload, and it binds someone going through this UI rather than someone with the file. Anyone who can use this browser profile AND knows the PIN can read this account's records without the password, and script that gets to run on that origin can use the keys for as long as a tab holds them. It is off unless asked for, it is cleared by signing out and by "forget", and revoking the browser in Devices is what ends it from anywhere else.
- Web sessions are isolated by `BrowserContext`, one per user and Space, sharing a Chromium per worker as runs already do. Per-user containers are a deployment milestone ([architecture](architecture.md), production sequence), so a Chromium-level escape on a worker is not currently contained to one account.

## Release gates

- Production request interception and redirect-hop credential stripping tests in real Chromium.
- Capsule expiry and revocation tests across broker, runtime, and egress gateway.
- Cross-device approval replay, expiry, double-consumption, and stale-policy tests.
- Sub-second takeover measurements on the hosted live-view path.
- KMS key anchoring and independent evidence-bundle verification.
- CHIPS, localStorage, and IndexedDB compatibility matrix with fail-closed capture.
- Two-device convergence, exclusive-lease deferral and release, and revocation tests against the real control plane and hub (in repository), repeated against production Postgres with a locale collation.
- Suma copyright/relicensing confirmation.
