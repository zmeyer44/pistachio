# Cloud browser, session sync, and identity egress

Revision 3, after the live Fly migration (text marked **(R3)**). This is the implementation spec for four features that land together:

1. End-to-end-encrypted cross-device sync of cookies (sessions), Spaces, and tab state.
2. A control plane with email + password accounts (BetterAuth), device enrollment, signed device tokens, wrapped-key storage, and device revocation.
3. A cloud browser (Playwright Chromium) that runs the agent when no desktop is online. It is a full sync device with its own keys, takes exclusive origin leases while it drives, streams a live view to the desktop, and accepts runs from an authenticated webhook channel.
4. A per-user static-IP egress gateway (HTTP CONNECT proxy) so the desktop and the cloud browser present the same IP to every site.

Most of the code is lifted from the sibling Suma repository (`~/harbor`), which ships (1), (2), and most of (3). Where this document and harbor disagree, this document wins; where this document is silent, copy harbor.

Every section below is normative. Package names, routes, frames, key names, env vars, and file locations are fixed so that independently implemented parts fit. Text marked **(R2)** changed in this revision.

## 0. Decisions

| # | Decision | Choice |
|---|----------|--------|
| D1 | Hub hosting | HubCore runs **in the control-plane process** over a `ws` server attached to the Hono node-server. Storage is a Postgres/PGlite `hub_kv` table with a `COLLATE "C"` key and an in-process per-user chain. Single replica for v1. No Cloudflare. |
| D2 | zod | zod 4 everywhere. No `@hono/zod-validator`; a `validate(schema)` middleware in control (§7.9). |
| D3 | Domain separation strings | Renamed from `suma.*` to `pistachio.*` atomically. The record-seal AAD, workspace AAD/signature layouts, and `__workspace__` pseudo-space live in the protocol package. |
| D4 | Package placement | New sibling packages; `@pistachio/protocol` stays dependency-free. `services/*` added to the workspace. |
| D5 | Key wrappers | Kinds produced: `password`, `recovery-code`, `device-x25519`. Password wrappers re-wrap on password change and are purged on password reset. |
| D6 | Cloud device key custody | Every device has an Ed25519 signing key **and** an X25519 agreement key. When a user enables the cloud browser for a Space, an enrolled Mac or web device that has opened the Space wraps its root secret to the cloud device's X25519 public key with a **sender-signed** `device-x25519` wrapper (§2). The server never sees plaintext keys. **(R2)** Trust assumption: control is trusted to introduce the cloud device's public key on first enable; the desktop pins it (`cloudDevicePin`), while the web flow verifies the enrolled recipient and the Devices UI exposes fingerprints so substitution is visible. |
| D7 | Enrollment | One call: `POST /v1/devices/enroll` carries the client-generated device id, both public keys, and a signature over `deviceLoginSigningBytes(deviceId, challenge)`, verified against the public key **in the body**; the response is a signed device token. No `hbr_dev_` stubs anywhere. `CONTROL_TOKEN_SK/PK` are required by `server.ts`; `dev-server.ts` generates an ephemeral pair with a loud warning; tests generate a pair. |
| D8 | Space identity | Control `spaces.id` is **text**, client-authoritative, validated by `^[a-z0-9][a-z0-9-]{0,63}$` **or the reserved `__workspace__`**. The default Space `work` converges across devices by construction; forks are uuids. |
| D9 | Tab sync scope | Per-device sealed restore points (`DurableTabSession`) with Pull/Merge; no live per-tab registers. Spaces are global LWW docs. Sidebar shelf sync is out of scope. **(R2)** "Push" means "publish this device's restore point now"; there is no canonical tab graph. |
| D10 | Lease arbitration | The cloud device takes **exclusive** leases for every origin it writes and renews them while a run is active. The hub denies forced takeover against a live exclusive lease whose holder has an open socket. Desktop engines **defer** instead of force-taking when the holder is a cloud device. `kind` is bound server-side from `devices.platform`, never from the client. |
| D11 | Where the agent loop runs for cloud runs | The cloud-browser service hosts the loop. `ai-agent-runner.ts` and `thread-context.ts` move into `@pistachio/agent-runtime` behind a `BrowserBackend` interface. The desktop observes cloud runs through the control plane. |
| D12 | Live view | Dedicated WebSocket from desktop main **and from the account web app** to the fleet's one public address, authorised by an opaque single-use `live-ticket` (no WebSocket client can set a header, so the credential rides in the URL and must authorise nothing else). Whichever worker takes the socket relays it to the leaseholder over the private network, and the viewer must prove it holds the run's Space key before a frame is sent. CDP `Page.startScreencast` frames; `Input.dispatch*` for takeover, from either client. Rendered in a renderer `SurfacePage` overlay on the Mac, and beside the thread on the run page on the web. |
| D13 | Egress topology | One gateway host per user (static egress IPv4), reached as an `https://` proxy. Credentials are HMAC Basic-auth pairs minted per device (and per run for the cloud) with a 24 h expiry, a credential id, and a revocation feed. Fail closed: no `direct://` fallback. QUIC disabled process-wide; WebRTC `disable_non_proxied_udp`. |
| D14 | Main-process fetches | Control, hub, and model traffic go direct. **(R2)** Page reads for identity-routed Spaces use `net.request` on the Space session with a per-request `login` listener; `session.fetch` is never used for proxied traffic. |
| D15 | Verifier | `DeviceRegistryVerifier('reject')`, fed from `GET /v1/devices`, keyed by the one device id (D24). |
| D16 | Engine persistence | `SpaceSyncEngine` takes an injected `QueueStorage`; the desktop backs it with a JSON file per Space that also persists the HLC clock. |
| D17 | Origin corpus | Ship `SEED_CORPUS`; untested origins default to synced (tier 1, not rotating-auth); sensitive origins stay tier 0. Served from `GET /v1/sync/policy` with a bundled fallback. |
| D18 | Channel ingress | Generic authenticated webhooks stay Space-bound. The account-scoped BlueBubbles connector links one phone by OTP and sends only agent questions and terminal completions; its boundary deterministically renders rich questions as plain text and maps the reply back to the pending question without changing agent code. |
| D19 | Env var for control | `PISTACHIO_CONTROL_URL`. `PISTACHIO_API_URL` keeps meaning the marketing site. |
| D20 | Desktop secrets | `<userData>/account.json` with `safeStorage`-encrypted secret fields. Egress credentials live only in memory. Nothing secret in `settings.json`. |
| D21 | BetterAuth exposure | Server-side API only. No HTTP handler mounted. |
| D22 | Gating | Everything in this spec is off until the desktop is enrolled. `PISTACHIO_E2E=1` never dials control, the hub, or a gateway. |
| D23 | Licensing | Suma is AGPL-3.0 and single-author (`zmeyer44`), the same author as Pistachio. Copied files carry the Pistachio license. The ledger records the confirmation as a release gate. |
| D24 **(R2)** | One device id | A device has exactly one identifier, a client-generated lowercase uuid v4 minted next to its keys and never changed. It is `devices.id` in control, the token claim `did`, `hello.deviceId`, `signer.deviceId`, `SyncEngineOptions.deviceId`, the HLC `deviceId` on every record, the `DeviceRegistryVerifier` key, `DevicePresence.deviceId`, `lease.*.holderDeviceId`, the `<deviceId>` segment of egress usernames, `executor.deviceId` on cloud runs, and the raw (not URL-encoded) `<id>` in `device-workspace:<id>` / `device-activity:<id>`. No component holds a second "control" or "local" device id. |
| D25 **(R2)** | Run content privacy | Page content, screenshots, messages, and URLs of cloud runs are stored on control only as content-class events sealed under the Space seal key. Control reads only control-class events. |
| D26 **(R2)** | Policy on cloud runs | v1 cloud runs enforce the SSRF network policy and the egress gateway policy. `PolicyEnforcer` (semantic approvals) is not bound on the cloud path because there is no adapter registry for arbitrary origins. The agent completes explicitly requested checkout, payment, consent, and final-action controls itself; `request_takeover` is a last-resort technical fallback only for person-bound steps the browser tools cannot operate. |
| D27 | Credential handoff | A cloud run may request a 15-minute, one-use form for passwords, authentication codes, payment details, recovery secrets, or other sensitive editable fields. The unguessable capture URL is the bearer capability, so it works without an account session or unlocked Space. The web client uses an ephemeral X25519 key to seal the values directly to the assigned cloud device's enrolled public key; control stores ciphertext only; that device consumes it once and types it into preflighted, origin-bound controls. `AgentTakeover.kind = 'credentials'` carries a host-authored `captureId`; clients and iMessage notifications construct the route from a configured Pistachio web origin and never turn model-authored instructions into a link. |
| D28 | Credential vault | What a person hands to a cloud run through the D27 form may be kept for the next run on the same site, when they leave the form's "keep in my vault" choice on (the choice rides inside the sealed payload; control never sees it). After a complete injection the cloud device seals the storable fields (never a one-time code) under the **Space seal key** with `vaultEntrySealAad(spaceId, entryId)` and files them through a lease-scoped internal route; control stores field names, purposes, and ciphertext only. On a later `request_credentials` the runner looks the origin up, and when one entry covers every requested field (matched by purpose: `username`/`email` are one sign-in id, a password is the site's password, otherwise type + label) it opens the entry with the Space key, types the values into the preflighted controls, and returns to the model without a pause; the model learns only that the fields were filled. An entry the run has already typed is not typed again in that run — the next request goes to the person, whose answer supersedes every older entry for the origin whose purposes it covers. The person reads, edits, adds, and removes entries per Space in Settings → Vault on the web and on the Mac, opening them with their own copy of the Space key; the cloud device is kept off the account-wide listing by the bearer gate. |
| D29 | Dedicated integrations | A third-party service the agent reaches through its API with a grant the person made — Gmail first — rather than by driving its site in a tab (docs/integrations.md). One connection per provider per Space, at an access level (`read` / `write` / `send`) that decides both the OAuth scopes asked for and the tools registered. The desktop runs the installed-app authorization-code flow with PKCE against a loopback redirect, seals `{version: 1, refreshToken}` under the **Space seal key** with `integrationConnectionSealAad(spaceId, connectionId)`, and files it at `PUT /spaces/:id/integrations/:connectionId`; control stores provider, account label, access, granted scopes, status, and ciphertext, and hands enrolled devices the operator's OAuth client (`INTEGRATION_<PROVIDER>_CLIENT_ID` / `_CLIENT_SECRET`, an installed-app client whose secret the provider does not treat as confidential). Each executor opens the grant with the Space key, mints access tokens in memory for one run, and never stores them; the model sees only the account's name and level. A grant the provider answers `invalid_grant` for is marked `reconnect_required` by exact id; disconnecting from the Mac revokes it at the provider and deletes the row; disconnecting from the web, which holds no key, leaves a `revoke_pending` tombstone that no executor binds, that a bound host notices within 30 s, and that the next device able to open the grant revokes and deletes. |

- `publishRejected(recordId, reason)`: for `lease_required` / `exclusive_lease`, first acquire without force. If denied and `deferToForeignLease(denial)` returns true, park the record's current wire in the `deferred` lane. For `reason: 'timeout'|'offline'` outcomes, park in `deferred` as well (never force on an unknown holder). Otherwise harbor's forced-takeover path runs.
- Deferred lane: drained only by `leaseReleased(originId)` / `leaseRevoked(originId)` for that origin, `setOnline(true)`, and a host-driven `retryDeferred()` the desktop calls every 30 s. A drained deferred record whose current winner is no longer authored by this device or is a deletion cause is dropped; a `stale` ack drops it; another `exclusive_lease` rejection re-parks it without re-acquiring. `flushPending()` / `runDrainQueue()` drain only the default lane.
- `leaseReleased(originId)`: new transport input (hub `lease.released`). If `originId` is in the engine's own `grantedLeases` it is removed; the next write re-acquires.
- **Unpublished versions never appear as `causalParent` on the wire.** Ancestry edges carry `{parent, unpublished}`. `unpublished` is true for a local version stored `localOnly` or handed to either queue lane instead of published; false for the exact wire passed to `transport.publish`. A single choke point `publishWire(wire)` runs `relink(wire)`: follow ancestry from `wire.causalParent` while the token is `unpublished`; if the parent changes, rebuild the wire with the new parent, re-sign (`sealedRecord`, `hlc`, `cause`, ids unchanged), overwrite the local edge, and replace `records[recordId].wire` when the HLC matches. Invariant: every published `causalParent` is `null` or a token this device published or received from the hub. `OfflineQueue` keeps newest-per-record compaction and stays crypto-free.
- `QueueStorage` file schema (desktop implementation): `{version: 1, clock: Hlc | null, offline: CookieRecordWire[], deferred: CookieRecordWire[]}`, written atomically. The engine writes `clock` after every `clock.send()` used to build a wire, and the constructor calls `clock.restore(file.clock)` before any send.

### 7.2 Auth model **(R2)**

- Bearer tokens are device JWTs from `@pistachio/sync-protocol` `signDeviceToken` with claims `{sub: userId, did: deviceId, iat, exp, jti}`. A **bootstrap** token has `did === sub`, is issued by signup and password login, and cannot be refreshed once the user has an active device.
- `authenticateToken(db, signing, token): Promise<{userId, deviceId: string | null, platform: 'macos'|'web'|'cloud'|null, revoked: boolean} | null>` re-reads `users` and `devices` on every request; `platform` comes from `devices.platform`, never the token. HTTP routes map `revoked` to 401; the hub host maps it to 4003.
- Route families never cross (copy harbor's dispatch): `/v1/internal/*` accepts only `CLOUD_BROWSER_SERVICE_TOKEN` (`bearerService`); `/v1/usage/egress`, `/v1/egress/revocations`, `/v1/egress/limits` accept only `EGRESS_GATEWAY_TOKEN`; `/v1/channels/:linkId/inbound` accepts only the link secret; every other route accepts only device/bootstrap JWTs. Service tokens compare with `timingSafeEqual`.
- `/v1/ai/*` (`ai-proxy.ts`) is the desktop's model path: a device JWT (never bootstrap, never a cloud device) in, and the request forwarded to the Vercel AI Gateway under control's own `AI_GATEWAY_API_KEY` with the `ai-*` protocol headers kept and the answer streamed back. The desktop's `createGateway` is pointed at `<control>/v1/ai` and holds no provider key of its own; the cloud browser keeps its own key. With no key configured the family answers 503. Every request is metered per user in `ai_usage`; a device reads its account's totals at `GET /v1/ai-usage`. The kind is the first path segment past the prefix (`usageKindOf`), so the family covers whatever the SDK posts: `/v1/ai/language-model`, `/v1/ai/embedding-model`, `/v1/ai/speech-model`, `/v1/ai/transcription-model`, `/v1/ai/evaluation-model` — the address bar's intent model (docs/smart-suggestions.md), reached with `experimental_evaluate` and `ai-evaluation-model-specification-version: 4`, whose JSON answer carries the same `usage` and gateway `cost` every other kind does — and anything else as `other`. Its model id is `PISTACHIO_INTENT_MODEL` (default `typesafe-ai/jev`; `off` disables it), read by the desktop and by each cloud-browser worker.
- Tiers on JWT routes:
  - **Bootstrap-allowed** (deviceId may be null): `POST /devices/enroll`, `GET /me`, `GET /spaces`, `GET /spaces/:id/wrappers` (so a second device can unwrap before enrolling), `POST /auth/token/refresh`.
  - **Device required**: every other JWT route; `requireDevice` middleware returns 403 `{error:'device_required'}` when `deviceId === null`.

On `run_events` appends: `question.asked` → `kind:'judgment'`, `takeover.requested` → `kind:'approval'`, terminal `status` → `kind:'completion'`, `reply` → `kind:'reminder'`; `actionUrl = <CONTROL_PUBLIC_URL>/runs/<runId>`, `capabilityCeiling: []`. `ChannelWebhookAdapter` (`id: 'channel:<linkId>'`) POSTs `{runId, kind: {judgment:'question', approval:'approval', completion:'done', reminder:'reply'}[kind], text}` to `outbound_url` with headers exactly `Content-Type: application/json`, `User-Agent: pistachio-control`, `X-Pistachio-Delivery: <idempotencyKey>`, `Authorization: Bearer <link secret hash prefix is NOT sent; send nothing>`; `redirect: 'error'`, 10 s timeout, body discarded, max 3 attempts. `vetOutboundUrl(url)`: `https:` only (`http:` to `127.0.0.1`/`localhost` allowed when `NODE_ENV !== 'production'`), no credentials, port 443/unset, hostname not an IP literal and passes `!isLoopbackHost && !isPrivateHost`. Before **every** dispatch resolve with `dns.lookup(host, {all: true})`, reject if empty or any address fails `checkResolvedAddress`, and dial only the vetted addresses (undici `Agent` with a custom `connect.lookup`).

iMessage is a separate connector boundary for task requests, questions, completion text, and secure-information alerts. An unknown sender receives a 30-minute, single-use `<PISTACHIO_WEB_URL>/onboarding/imessage#<secret>` capability. Control stores only its SHA-256 digest; the fragment does not reach the Next server, and claiming it after password authentication atomically links the already-verified phone to the selected account. A linked sender's text answers the newest pending question when one exists. Otherwise control classifies it against up to three of the threads that phone recently addressed (cloud runs in the default Space, neither revoked nor rejected, active within 7 days): the runner opens each thread's message rows, a model says whether the text continues it, and the most confident continuation receives it as a sponsor message (reopening a completed, failed or interrupted run); anything else creates an idempotent cloud run in the default Space. When a credential pause commits, the runner forwards only the host-authored `captureId`; control reloads the inspected origin and requested field labels from `credential_captures`, builds `<PISTACHIO_WEB_URL>/credential-capture/<captureId>` itself, and sends that link with an instruction not to reply with secrets. Connector failure is logged after commit and never rolls back the pause.

### 7.6 Egress provider and credentials **(R2)**

`EgressProvider { provision(userId, region): Promise<{host, port, egressIp}>; destroy(userId) }` with `StaticEgressProvider` (`EGRESS_STATIC_HOST`/`PORT`, one shared gateway) and `FlyEgressProvider` (per-user app `pa-eg-<userId>`; `FLY_API_TOKEN` — an **org-scoped** token, app creation needs it; `FLY_ORG_SLUG`, `FLY_EGRESS_IMAGE`; sets app secrets `EGRESS_TOKEN_SECRET` and `EGRESS_OWNER_USER_ID`). **(R3)** Fly's split API surface is load-bearing: apps, machines, and restart go through the Machines REST API (`api.machines.dev/v1`); secrets (`setSecrets`) and every IP operation go through GraphQL (`api.fly.io/graphql`) because neither ever shipped in the REST API — there is no `GET /apps/:app/ips`. Provision order, each step an idempotent ensure so a crash between Fly and the `egress_gateways` insert re-runs cleanly: ensure app (`GET` then `POST /apps`; a fresh app 404s machine creation briefly — retried); `setSecrets` **before** the machine exists, because a machine's environment is fixed at create and the gateway refuses to serve without its verifier; ensure machine; ensure the app-scoped **static egress IPv4** (`allocateEgressIpAddress` in the machine's region — this dedicated exit address is `egressIp` and the identity IP of D13; a fresh allocation takes minutes to bind, so the machine is restarted to make it immediate; never allocate a second one in the region, machines pick between them at random per destination); ensure inbound anycast (`allocateIpAddress`: one free `shared_v4` and one `v6`, without which `<app>.fly.dev` never resolves and every client dies at DNS). `destroy` deletes the app (404 tolerated), which releases machines and both IP kinds in one call. The image is built from `Dockerfile.egress` via `fly deploy -c fly.egress-image.toml --build-only --push` into the machine-less `pistachio-egress` registry app.

Credential v1: `username = 'pe1.' + userId + '.' + deviceId + '.' + credentialId + '.' + expUnixSeconds` — three lowercase uuids and decimal seconds; parsers require exactly five dot-separated fields. `key = Buffer.from(secretHex, 'hex')` (32 bytes); `password = base64url(HMAC-SHA256(key, utf8(username)))` without padding (43 chars). `credentialId` is the `egress_credentials.id` inserted at mint with `expires_at = now + 24 h` and the optional `run_id`. Gateway secret: `EGRESS_PROVIDER=static` → control's `EGRESS_TOKEN_SECRET` literally (shared with the gateway); `fly` → `HKDF-SHA256(ikm = bytes(EGRESS_TOKEN_SECRET), salt = '', info = 'pistachio-egress/' + userId, 32)` as lowercase hex; control recomputes at mint time and stores nothing.

### 7.8 Run event contract **(R2)**

- Runners seal every `RunContentEvent` as `{t:'sealed', spaceId, sealed: base64(seal(spaceKeys.sealKey, utf8(JSON.stringify(plain)), runEventSealAad(runId, eventId)))}` — the AAD binds `eventId` (not `seq`, which control allocates). The optional `kind` names the sealed event's type (`message`, `tool.detail`, …) so control can pick conversation rows for the iMessage router without opening anything. Control never opens sealed events and persists no `data`, `dataUrl`, `summary`, `messages` keys in plaintext.
- `hosted_runs.thread` is `{spaceId, sealed}` with AAD `runThreadSealAad(runId)`, media stripped, capped at 2 MB; only the runner opens it.
- `seq` is allocated by control inside the append transaction: `UPDATE hosted_runs SET next_seq = next_seq + $n WHERE id = $1 RETURNING next_seq` then `INSERT … ON CONFLICT (run_id, event_id) DO NOTHING`. Runner appends are lease-checked; `cmd.*` appends are sponsor-checked. Size cap 64 KiB per event.
- `hosted_runs.summary` is `foldControlSummary` applied by control on every append (feeds `GET /runs` and `ThreadListItem`). The desktop folds the full `RunSummary` with `foldRunEvent` after opening sealed events with `spaceSecrets[spaceId]`; a device without that Space's secret renders control-class rows only.
- SSE `GET /runs/:id/events?since=<seq>`: `Content-Type: text/event-stream`; frames `id: <seq>\nevent: run\ndata: <JSON StoredRunEvent>\n\n`; `since` or `Last-Event-ID`; `: ping` every 15 s; `event: end` when terminal. - Long-poll `GET /internal/runs/:id/commands?since=<seq>&wait=25` returns immediately when non-empty else after `wait` seconds with `[]`.
- Retention: `run_events` deleted and `thread` cleared 30 days after `completed_at`.

### 8.1 Process model **(R2)**

One Node process, one Chromium: `chromium.launch({executablePath, headless: true, proxy: {server: 'per-context'}, args: ['--disable-quic', '--force-webrtc-ip-handling-policy=disable_non_proxied_udp', '--disable-dev-shm-usage']})`. One `UserSession` per `(userId, spaceId)`: a `BrowserContext` from `browser.newContext({proxy: {server: 'https://<host>:<port>', bypass: '<-loopback>'}, serviceWorkers: 'block', acceptDownloads: true, viewport: {width: 1280, height: 800}, ignoreHTTPSErrors: false})` — **no `username`/`password` on the context and no `httpCredentials`** (Playwright would present them to any origin 401) — plus a `SpaceSyncEngine` (`leaseKind: 'cloud'`), `PlaywrightCookieApplier`, and `PlaywrightCookieCapture`. Contexts are created on run claim and closed 10 min after the last run for that space ends. One `WsTransport` per user (per cloud device) declaring active spaces via `updateSpaces`.

**`acceptDownloads: true`, and the gate is on the page, not on the context.** One `BrowserContext` per user and Space serves runs and browser sessions alike (W11), so the context cannot refuse downloads without refusing the sessions'. What it accepts is not what it keeps: `PlaywrightBrowserBackend` registers a `download` handler on every page it opens which **cancels** the download unless a session host has claimed the context (`claimDownloads()`, released when the host closes). Only a session host has somewhere to put the bytes (`CLOUD_BROWSER_STATE_DIR/<userId>/downloads`), a policy verdict to apply and a retention sweep behind it. A download that starts on the ordinary hosted-run path — no session, no host — is cancelled where it starts, so a hostile page an agent visits cannot fill the worker's disk. See [web-browser-design.md](web-browser-design.md) §11.

Network guard (modified harbor `#installNetworkGuard`): the per-page guard `CDPSession` is the **single owner** of network interception and authentication. Before enabling, register `Fetch.authRequired`: if `authChallenge.source === 'Proxy'` and `new URL(authChallenge.origin)` matches the gateway host:port → `Fetch.continueWithAuth({requestId, authChallengeResponse: {response:'ProvideCredentials', username, password}})` reading the session's **current** credential; otherwise `{response:'CancelAuth'}`; a second consecutive proxy challenge for the same request is cancelled and triggers a credential refresh. Then `Network.enable`, `Network.setBypassServiceWorker({bypass: true})`, and `Fetch.enable({handleAuthRequests: true, patterns: [{urlPattern:'http://*', requestStage:'Request'}, {urlPattern:'https://*', requestStage:'Request'}]})`. `Fetch.requestPaused` → `SafeBrowserNetworkPolicy.assertAllowed` → `continueRequest` / `failRequest({errorReason:'BlockedByClient'})`. No `page.route` anywhere.

### 8.2 Device identity **(R2)**

Provisioning is push-driven by control, never lazy. `POST /v1/devices/provision {userId, nonce}` (service bearer) runs under a per-user mutex: if `CLOUD_BROWSER_STATE_DIR/<userId>/device.json` exists and a token refresh succeeds, return the stored device; otherwise generate `deviceId = randomUUID()`, Ed25519 + X25519 keypairs, obtain a challenge from `POST /auth/device-challenge {deviceId}`, sign it, call `POST /internal/cloud/devices/enroll {userId, nonce, deviceId, devicePublicKey, agreementPublicKey, challenge, signature}`, write `device.json = {version: 1, userId, deviceId, signingKey (JWK), agreementKey (JWK), devicePublicKey, agreementPublicKey}` encrypted with `CLOUD_BROWSER_STATE_KEY` (AES-256-GCM), and return 201 `{device}`. On 409 `cloud_device_exists` discard the keys and return 409.

Tokens: `device-challenge` + `device-login` proof-of-possession, refreshed at `exp − 60 s` via `/auth/token/refresh`. Space root secrets: `GET /spaces/:id/wrappers` (and `/spaces/__workspace__/wrappers`) with the device bearer; select `kind === 'device-x25519' && credentialId === deviceId`; resolve `senderDeviceId` against `GET /devices` (cached ≤ 60 s), require `platform === 'macos'|'web'` and `revokedAt === null`; `unwrapRootSecretFromDevice(...)`. Failure logs `wrapper_rejected {spaceId, credentialId, senderDeviceId, reason}` and fails the run with `no_space_key`; secrets are held in memory only. The runner builds `DeviceRegistryVerifier('reject')` from `GET /devices` before hydration and refreshes it on the first unknown-device rejection.

Revocation: on steer `device.revoked` (matching stored identity), hub close `4003`, or 401/410 from control for the device, the runner runs `onDeviceRevoked(userId)`: fail active runs via `/internal/runs/:id/fail {reason:'device_revoked'}`, close live-view sockets `4003`, release held leases if the hub socket is open then stop the transport, close every `BrowserContext` for the user and discard proxy credentials, zeroize unwrapped secrets and `SpaceKeys`, delete `device.json`. A revoked identity is never reused. A claimed run whose user has no stored device or whose token refresh fails is failed with `cloud_device_missing` before any context is created; the runner never enrolls from the claim path.

Egress credentials: per run via `GET /internal/users/:id/egress-credential?deviceId=<cloud device>&runId=`; kept in the `UserSession` and re-read by the guard on every challenge.

### 8.4 Agent loop **(R2)**

### 8.5 Live view **(R2)**

`GET /v1/live/:runId` WebSocket, served by **any** worker in the fleet behind its one public address. Upgrade auth: an opaque ticket from `Authorization: Bearer` (native clients) or `?access_token=` (deleted before logging). After the handshake the viewer's device is re-checked every 60 s with `GET /internal/devices/:deviceId`; close `4003 revoked` when missing/revoked/other user; `device.revoked` steer closes matching sockets immediately.

**Origin.** An upgrade carrying an `Origin` header must match `PISTACHIO_WEB_URL`'s origin, else 403 — checked first, so a page on another origin is refused whatever it holds. A native client sends no `Origin` and is unaffected.

**Tickets, not tokens.** Neither Electron main nor a browser can set a header on a WebSocket, so the credential rides in the URL — where it reaches `performance.getEntries()`, extensions, and every proxy in between. It therefore authorises nothing else: `POST /v1/runs/:id/live-ticket` (device bearer; 403 for a bootstrap or `cloud` device, 404 unowned, 409 `not_a_cloud_run`/`not_running`, 503 with no `CLOUD_BROWSER_PUBLIC_URL`) returns `{url, ticket, expiresAt}` where `ticket` is an opaque `plt_` secret, stored hashed in `live_tickets`, good for **one run, one redemption, one minute**. `authenticateToken` never accepts it — it is not a JWT — so it is not a bearer for any other route and cannot be replayed onto the user's other concurrent run. The runner spends it through `POST /v1/internal/live-tickets/redeem {ticket, runId}` (service bearer), whose single `DELETE … RETURNING` *is* the authentication; the answer carries the viewer's identity, the run's Space, and the leaseholder's private address, so one round trip both authenticates and routes. A device revoked between issue and redemption is refused. Both clients fetch a fresh ticket for **every** dial, including reconnects, so a re-claimed run is followed to its new worker. Unspent tickets are swept by `runMaintenance`.

**Proof of the Space key.** A device token gets you a socket; the Space key gets you the picture. On accept the runner sends `{t:'challenge', spaceId, nonce}` and nothing else — no status, no tabs, no frames — until the viewer answers `{t:'auth', proof}` with base64 `seal(spaceKey, utf8(nonce), liveProofSealAad(runId, nonce))`. The runner holds the same key (it is driving the run under it) and opens the proof; a wrong answer, or ten seconds of silence, closes `4004` with `space_key_required`, and the nonce is not reissued. This is what makes key possession a real boundary rather than a UI courtesy: an enrolled device of the owner that cannot open the Space cannot watch it either, which is exactly the rule the thread follows. Both clients seal with the key they already read the thread with.

**One address, any worker.** The live-run registry is in-process (`executor.runFor(runId)`), so the worker that takes the socket may not be the one holding the run. It relays: the leaseholder's private `workerUrl` — recorded on the lease at claim time from `CLOUD_BROWSER_INTERNAL_URL`, part of `RunLease` so it dies with the lease — is dialled at `/v1/internal/live/:runId` with the service bearer and the already-authenticated identity in the query. That internal path serves only runs it holds and never relays onward, so there is no ring. Frames pass through untouched, so the Space-key challenge stays end-to-end between the viewer and the worker holding the key: the hop can neither answer it nor read what it protects. The upstream is dialled **before** the viewer's handshake completes (a viewer whose target is gone is refused at the handshake, not accepted and dropped), so the holder's opening challenge is buffered until there is a downstream to forward it to. The fleet needs no per-worker public DNS and autoscales freely.

**Keepalive.** The server pings every 25 s and terminates a socket that misses two (`DEFAULT_PING_INTERVAL_MS`); a relayed socket is pinged by the gateway too, since ping and pong are per connection and the holder's stop at the hop. A screencast is silent whenever the page is, and every load balancer culls idle connections — ALB and nginx default to 60 s — so without this a browser watching a static page is disconnected on a timer. Browsers answer pings at the protocol level; the page never sees them. Deployments must keep the proxy's idle timeout above the ping interval and terminate TLS in front of the fleet (clients derive `wss://` from an `https://` public URL).

**Lease tokens.** `GET /v1/runs/:id` blanks `lease.token` before answering a device: it is a worker credential, paired with the service bearer on `/internal/runs/*`, and no client reads it.

Frames: server → client `{t:'frame', data: base64 JPEG, width, height, metadata: {deviceWidth, deviceHeight, pageScaleFactor, scrollOffsetX, scrollOffsetY}}` from `Page.startScreencast({format:'jpeg', quality: 60, maxWidth: 1280, maxHeight: 800, everyNthFrame: 2})` on the guard session (`Page.screencastFrameAck` after each), `{t:'tabs', tabs: AgentTabInfo[], activeTabId}`, `{t:'status', status: TaskStatus, control: 'agent'|'human'}`, `{t:'error', code: 'unauthorized'|'not_found'|'ended'|'space_key_required', message}`. Client → server `{t:'input', event: {kind:'mouse', type:'mousePressed'|'mouseReleased'|'mouseMoved'|'mouseWheel', x, y /* CSS px, client-scaled: x = offsetX * metadata.deviceWidth / width */, button: 'left'|'middle'|'right'|'none', clickCount, deltaX?, deltaY?, modifiers}}` or `{t:'input', event: {kind:'key', type:'keyDown'|'keyUp'|'char', key, code, text?, windowsVirtualKeyCode?, modifiers}}`, `{t:'focus', tabId}`. Inputs are forwarded to `Input.dispatchMouseEvent/KeyEvent` only while `control === 'human'`; dropped otherwise.

## 15. Corrections after the implementation review (normative)

An adversarial review of the built code found fifteen confirmed defects that the passing test suites did not catch. All are fixed and pinned by regression tests. This section records what the code now does where it differs from, or refines, the sections above.

**Sync engine (§3).** The "unpublished" bit is retracted, not only set. When a `publish.ack` reports a rejection, the engine un-marks the versions it had sent for that record so a wire the hub refused can never remain a legal `causalParent` — otherwise a peer holding a deletion fence blocks the whole later chain forever. Un-marking stops at the record's newest deletion fence: relinking past a fence can only turn a peer's `descends` verdict into `predates`, so walking further back never helps and would break convergence. Accepted record ids from `publish.ack` are reported to the engine, so the in-flight window is exact rather than heuristic. A lease renewal that ends in `timeout` or `offline` keeps its cached grant; only a hub denial evicts it, because an unknown holder is not evidence that the lease was lost, and evicting it would silently drop exclusivity and demote a genuine logout mid-run.

**Publish rejections (§2, §3, §4).** `PublishRejection.reason` gains `rate_limited` and `unknown`, and the wire field parses with a fallback to `unknown` so a reason a newer hub adds can never drop a whole `publish.ack` frame. The hub reports an over-quota publish as `rate_limited`, not `stale`: `stale` means the hub durably holds a newer version, and treating a throttled record as durable dropped it forever. The engine re-queues a `rate_limited` or `unknown` record in the default lane (not the deferred lane, whose depth gates the desktop's manual push) and both hosts flush that lane on their retry tick. An unrecognised reason is never treated as durable. **Rollout order:** the reason set widened compatibly forward but not backward, and `hello` carries no protocol version, so the hub and every client ship together for this release; a mixed deployment would need a capability field on `hello` first.

**Control (§7.1, §7.3, §7.8).** `devices` carries `revocation_completed_at`, and revocation is repair-on-retry: the database effects commit before the hub call, and a revocation that failed part way is completed by the next attempt rather than being suppressed by an idempotency guard. `hosted_runs` and `channel_links` reference `spaces` with `ON DELETE CASCADE`, so deleting a Space no longer fails once it has a run or a channel. Sponsor command events carry a unique id per append instead of colliding when the run revision has not changed. An `Idempotency-Key` first reserves `(run, operation, key)` in `run_sponsor_commands` inside the transition transaction, then stores the status and sequence response; retries replay that response before any coordinator mutation, steer, or audit. `GET /internal/runs/:id/commands` advances `since` past non-command events, so the long-poll neither rescans the run on every append nor blinds itself past the page limit. The pause payload is closed to the correlator fields the runner actually sends, so no writer can put plaintext prompts into control's plaintext store. Desktop egress credentials remain device-scoped, while cloud credentials require a live run and are never minted against a run that has already reached a terminal status. `egress_revocations` is pruned past a retention horizon, and a gateway whose cursor predates the horizon is told to restart from a full snapshot rather than silently missing revocations.

**Cloud browser (§8).** Question and takeover text reaches control only as sealed content; the pause payload carries correlator ids alone. Egress credentials are tracked per run rather than one slot per user, so a finishing run cannot revoke a concurrent run's tunnel.

**Egress gateway (§9).** Revocation catch-up drains multiple pages per tick, so a gateway restart cannot sit many minutes behind the feed while honouring stale credentials.

**Desktop (§10.1, §10.2, §10.3).** A sign-in that cannot fetch or open a Space's wrapper records that Space as key-less and refuses to mint a replacement secret for it. Minting one would have overwritten the account's real password wrapper — the default Space id is the same string on every install — leaving the account recoverable only by a recovery code the person was never prompted for, while the two devices silently diverged. The person is told to use their recovery code instead. A transient control-plane failure during the device-login proof is no longer read as revocation, so a network blip cannot erase a device token. A cookie record Chromium refuses to set is recorded and skipped instead of failing the hydration, which previously trapped the Space in a permanent full-rehydration loop against the hub; hydration applies records individually and stops re-dialing after three attempts. Workspace documents are signature-verified before their HLC is received, so a hostile hub cannot roll back Space documents or restore points. A Space with no root secret opens its hydration gate immediately rather than stalling the first page load for the full safety timeout. An identity-Space page read keeps the vetted, pinned address instead of re-resolving the hostname, which had reopened the DNS-rebinding hole the direct path closes.

**Publish rejection `clock_drift`.** The hub refuses a record whose physical clock is more than twice the drift window ahead of its own, and reports it as `clock_drift`, which the engine retries. The bound is deliberately wider than the client-side clamp: `HlcClock.receive` clamps a peer timestamp to exactly `wall + MAX_CLOCK_DRIFT_MS`, so a device that merged from a fast peer sits at that ceiling and would otherwise have every write refused the moment the hub ran a millisecond behind. Cookie records must carry the publishing device's own id; workspace documents must not, because an LWW register adopts the winner's HLC on merge. A device only ever publishes registers it authored, since re-signing a merged document with the local key under a peer's id yields a wire that fails verification at every peer.

**Late contract additions.** `TransportEvents` gains `onPublishAccepted(recordIds)`, fired from the `publish.ack` handler before that ack's rejections, and `SpaceSyncEngine` gains `publishAccepted(recordIds)`; both hosts wire it. With a real accept signal the in-flight window is exact, so the per-record cap it used to need is gone. `GET /v1/egress/revocations` gains `reset: boolean`, set when the caller's cursor names a row control has pruned. A gateway that sees it re-reads the feed from the start; it does **not** clear its revocation set, which only ever grows — clearing would briefly un-revoke a live credential, and every pruned row named a credential that expired weeks earlier and is already refused on expiry. `since=0` never resets, so the rewind cannot loop.

**Known limits, accepted for this release.** A `reset` can fire for a gateway that had already drained every pruned row; the cost is one redundant re-read per retention period. An approval-kind pause can no longer carry evidence fields through control, because closing the pause payload is what keeps model-authored text out of the plaintext store; if approval evidence ever has to cross control it belongs in a sealed content event. The publish-rejection reason set widened compatibly forward but not backward, so the hub and every client ship together for this release.

## 16. Second review pass

**Workspace HLC binding, restored.** §15 removed the hub's `doc.hlc.deviceId` check because merged registers carry the winner's HLC. The desktop fix that came with it — a device publishes only registers it authored — made every legitimate publish carry its own id, so the check is now both safe and necessary: the hub stores workspace winners by HLC and never opens `deviceSig`, so a doc attributed to a peer would park a winner that every device rejects on signature while suppressing that key's real updates. Cookie records were already bound; workspace docs are again.

**Sign-out drains before the jars are cleared.** Stopping sync returns a promise that settles once every in-flight `applyRemote` has finished. The generation check stops the next record, but one already inside Electron's cookie API would otherwise land after the partition was wiped and restore the signed-out account's cookie.

**Audits commit with their transition.** A sponsor command's audit row is written inside the same transaction as the transition and its cached idempotency response. Written afterwards it could be lost to a crash while the command stayed durable, and the replay path would then skip it forever, leaving a state change with no record of who made it.

**Writes are no longer lost when the socket dies.** A lease round trip that ends `offline` re-queues instead of publishing into a transport that drops the frame, and an interrupted publish re-queues our own deletions too. Dropping one loses a sign-out and leaves peers holding the dead session cookie; not forcing a lease takeover *for* a deletion is a separate rule and still applies.

**Paused runs are swept.** `runMaintenance` calls `expirePauses`. Nothing else did, so a run whose approval deadline passed could never be resumed, claimed, or ended, and its authority was never cut.

**A refused cookie update is refused.** The applier's read-back compares the value, not just name, domain and path. Playwright does not throw when Chromium drops a write, so an update to an existing cookie left the stale one standing and matching, committing a record the jar does not hold.

**Screencast frames are dropped, not buffered.** A viewer more than 4 MB behind skips frames. A frame is disposable and the runner shares its process with the runs.

**Four interface promises now hold.** The recovery code is shown by a component that survives enrollment flipping the account state. Deleting a cloud conversation stops following it, so its next event cannot restore it. The composer's Enter path is guarded while a send is in flight, so it cannot start two cloud runs. The sync page's origin table only clears when the Space changes, and merges rather than replaces, so a row the person looked up is not wiped by a background tab redirecting.

## 17. Personal records and the web app

**Three more doc kinds ride the workspace map.** `bookmark:<id>`, `reminder:<id>` and `memory:<id>` join the Space, settings and device docs as sealed LWW registers under the workspace pseudo-Space key. (S6 added a fourth and a fifth: `browser-session:<spaceId>`, a browser session's durable tabs and splits, and `shell-settings:default`, the shell's own settings as one account-global document — distinct from the per-field `settings:` registers, which a reader folds one field at a time. Both are specified in [web-browser-design.md](web-browser-design.md) §9 and §6.3.) They are account-global rather than per-Space, because a bookmark belongs to the person, not to one signed-in identity. Their wire shapes live in `packages/sync-protocol/src/records.ts` and are structural mirrors of the desktop's stores; `test/record-docs.test.ts` asserts mutual assignability in both directions, so the two definitions cannot drift apart silently.

**A memory's `isLatest` is derived on receipt, never trusted from the wire.** Each version is its own register keyed by its own id, and a receiving device recomputes the flag across the whole `rootId` chain — highest `version` wins. Trusting the transmitted bit would leave two latests when v2 arrives before v1, and none when a peer that pruned v1 re-serves it. A local correction therefore publishes two registers: the superseded version and the new one.

**The browser is a device, not a session.** Control mounts no BetterAuth HTTP handler (D21), so there is no cookie surface to sign a browser in with. The web app enrols itself as a device with `platform: "web"`, holding a non-extractable Ed25519 key pair in IndexedDB, and calls the same routes the Mac does with its own device token. Its Space keys are unwrapped in the tab from the account password; the password and the derived keys live in tab memory only, never in `localStorage`, `sessionStorage` or IndexedDB. A reload therefore lands in a `locked` state — enrolled and authenticated, but holding no keys until the person unlocks — *unless* the person chose "stay unlocked" at that unlock, which is the one exception and is opt-in: they are then asked, once the password has worked, to choose a six-digit PIN (`set-pin`), and this browser's IndexedDB keeps the Space ROOT SECRETS sealed under a PBKDF2-derived key from it for 30 days (`packages/web-account/src/{pin,vault}.ts`, `REMEMBER_DAYS`). Boot then lands in `pin` rather than `locked`: six digits, checked locally by whether AES-GCM opens the record, and a right one derives the same non-extractable Space keys a password unlock does. Five wrong ones destroy the record and the password is the only way back; a Space the account grew since makes the record stale and asks for the password anyway. Nothing usable is at rest — an earlier design kept non-extractable `CryptoKey` handles instead, which could not be read out but could be USED by anything that opened the origin, with no challenge at all. Signing out and "forget" clear them; revoking the browser in Devices ends it from elsewhere. What that buys and what it costs is a non-claim in [security.md](security.md). The Next server never sees a token, a password or a key, which keeps the end-to-end property intact with a server in the path.

**The browser can be the first device.** For an unprovisioned account it generates the Space and workspace root secrets locally, derives their keys, and uploads one atomic set of password-sealed wrappers through `/account/provision`. During the same password ceremony it may sign `device-x25519` wrappers for the hosted cloud browser, so account creation, encrypted-key setup, cloud enablement, and agent dispatch no longer depend on installing the desktop app. Remembered derived keys still exclude the root secrets; enabling a new Space after reload requires another password unlock.

**What an unlocked tab can do.** It reads workspace records over the hub with the same `WsTransport` the desktop uses, opens sealed run events so it can show what the agent read and wrote, and—during a password unlock, while root secrets exist in tab memory—can wrap a Space key for the enrolled cloud device. The browser signs that wrapper with its enrolled Ed25519 identity. Remembered derived keys alone cannot create another cloud wrapper, so enabling a new Space after reload asks for the password again.

**Credential capture is a dedicated capability route.** `/credential-capture/:captureId` needs no web account session: the random uuid and its 15-minute lifetime are the authority. It loads only bounded metadata from control, leads with the complete origin rather than the model's service label, and renders the stored field descriptors. The browser generates an ephemeral X25519 key, derives an AES-GCM key with HKDF domain `pistachio.credentialcapture.box.v1`, and seals `{version:1, fields}` directly to the cloud device public key, binding the envelope with `pistachio.credentialcapture.seal.v1` AAD. Control cannot decrypt it. The browser submits the ciphertext once and clears the controlled inputs after success. On failure the strings remain for an intentional retry and a visible “Clear form” action drops the UI references; the encoded `Uint8Array` is explicitly filled with zeroes, while JavaScript strings cannot be reliably zeroized.

**Both web apps build with webpack.** The workspace packages ship TypeScript source typechecked under NodeNext, so their relative imports carry the `.js` extension the emitted JS would have. Turbopack does not substitute the `.ts` on disk for a `.js` specifier, and this holds for files inside the app too, not just transpiled packages. Webpack does, through `resolve.extensionAlias`, so `dev` and `build` both pass `--webpack`. The alternative — dropping the extensions — would break `tsc` for every NodeNext consumer that pulls these files into its program.
