# Terminals

A terminal is a tab whose page is a shell on this Mac: zsh (or whatever the person's login shell is), fully capable — Claude Code, vim, htop, ssh, a dev server — drawn in a desk window like any page. The aim is Ghostty's feel: GPU-drawn text, the modern protocols programs ask for, and a terminal that knows where its shell is.

Desktop only. Builds on `docs/desk.md` (windows), `docs/spaces.md` (spaces, the sidebar) and the shell pages of `docs/notes.md` §4.

## 1. What a person does

**Open one.** ⌘J (*New terminal*, a configurable shortcut; also File › New Terminal and the address palette's *New terminal*) opens a terminal in a new tab of the space in use, its window out on the desk with the keyboard in it — what is typed straight away is the shell's. Opened from a terminal, the new one starts in that terminal's folder, as Ghostty's new windows do.

**Use it.** A login shell, so a Pistachio opened from the Finder still has the person's PATH. The tab is named by the shell: its folder at a prompt (`~/pistachio`), the command while one runs (`npm test`), or whatever a program calls itself (Claude Code). Over a terminal:

| Keys | |
| --- | --- |
| ⌘ anything else | The app's, as in Ghostty — ⌘T, ⌘W, ⌘L, ⌘J work over a terminal and never reach the program, even one that turned the kitty keyboard protocol on. |
| ⌘C / ⌘V | Copy the selection (with none, nothing — not the tab's address) / paste (bracketed, for programs that ask). |
| ⌘F | Find in the scrollback, as typed; Enter and ⇧Enter step, Escape closes. |
| ⌘K | Clear the screen and the scrollback (the host's copy too: a reload does not bring them back). |
| ⌘↑ / ⌘↓ | Jump to the previous / next prompt. |
| ⌘+ ⌘− ⌘0 | Type size, for every terminal (kept). |
| ⌘A | Select all. |
| ⌘-click | Open a link (a URL in the text, or a program's OSC 8 hyperlink) in a new tab. |
| ⌥-click | Move the cursor there in the line being typed. |

Option types what the Mac's keyboard puts on it (# € on many layouts, @ on a German one), as in Ghostty's and Terminal's defaults; ⌥← ⌥→ still jump by word.

**Told when it matters.** A command of at least ten seconds that ends while its terminal is out of sight says so in a notice (*“npm test” finished*, or *failed (exit 1)*) with *Show*; a program's own request to be noticed (OSC 9, OSC 777 — Claude Code's "waiting for you") does too. With the app in the background, the Mac's own notification as well.

**Gone and back.** The terminal belongs to its tab, not its window: collapsed into its row, carried off as the desk passes to another space, minimized, its shell runs on and it comes back as it was (scrollback, selection, a program in full screen). `exit` (or ⌃D) at the prompt closes the tab, as a terminal window closes with its shell; a shell that ended any other way (a signal, a non-zero code) says so in a note over the terminal's foot — beside its text, never written into it: the text is the host's, and a line of the window's own would put the next shell's output elsewhere in the window than in the copy a reload replays — and Enter starts a new one where it was, under the old one's scrollback — whatever keyboard mode the program that died left on (kitty's report-all-keys turns Enter into an escape sequence; Enter is read from the key itself), and with every mode it left on (its screen, synchronized output, mouse and focus reports, bracketed paste, the keyboard flags) reset first. A shell that ended while its terminal was out of the window (another Profile in front) is told when the terminal is opened again: its screen as it was, then how it ended — its tab closes then for a clean `exit`, as it would have. Closing the tab (⌘W, the row's ×) ends the shell. Quit and reopen: the terminal tab comes back with a fresh shell in the folder it was in.

## 2. The page

`pistachio://terminal/<id>` (twelve hex digits, `@pistachio/shell-contracts/terminal`) is a shell page (`shell-pages.ts`: `"terminal"`): the host keeps only the TAB — its row, its title (the shell names it through `setTabTitle`, which falls back to *Terminal*), its favicon, session restore — and keeps the tab's view down while the shell draws the pane. Tidy never sorts it, never counts it idle, never archives it (a shell may be serving or building; archiving would end it) — nor a favorite's group holding one: such a group is never idle, so the favorites' reset brings it down into the day's tabs instead of archiving it (`favoriteGroupsDue`, and `archivePageGroup` refuses it).

On the desk, `DeskWindow`'s `pageKind` is `"terminal"` and `ShellPageView` draws `TerminalPage` (`components/terminal/`), lazily — xterm.js and its addons (~900 kB) come with the first terminal opened. The page is a place to show the terminal, not the terminal: `lib/terminal/sessions.ts` keeps one xterm.js `Terminal` per terminal id for as long as its tab is in the shell's snapshot, and the page lends it an element (`attach`/`detach`; the latest page to ask holds it, and gives it back to the one before when it goes). So a window going home, the desk passing, a minimized window — each takes the element away and gives it back, and the terminal never stops. A terminal whose tab leaves the snapshot (closed, or in another Profile) is let go two seconds later.

The page fits the terminal to its box (FitAddon on a ResizeObserver, a frame later) except while the window is **frozen** — minimized (laid out at twice its size and scaled down), flying or closing — when the shell keeps the size it has: otherwise a minimize would reflow every program. The session knows it is frozen (`setFrozen`, as the page lays out), so nothing fits it meanwhile — not ⌘+ in another terminal (its type changes, not its rows and columns), not its first opening (at xterm's own size), not a replay (at the size it was replayed at) — and it is fitted as it thaws. It takes the keyboard when its window is in use (at once, while the window still flies in), unless its find bar has it.

The renderer: xterm.js **6.1 beta** (pinned, the set VS Code ships) — `@xterm/xterm` with WebGL (`addon-webgl`, custom glyphs for box drawing and Powerline), fit, search, web links, Unicode graphemes (`15-graphemes`), and the clipboard (OSC 52: questions answered empty here; copies are the host's to make, §5). The kitty keyboard protocol is on (`vtExtensions.kittyKeyboard`), synchronized output (DEC 2026) is xterm's own. A WebGL context is scarce (a page has some sixteen): a terminal nobody shows draws without one, and one that loses its context falls back to the DOM renderer.

Its look (`lib/terminal/theme.ts`): the ground is the window's own face (`--color-background-100`, resolved to a plain colour), the ink the shell's, the selection the Appearance's accent, the sixteen colours GitHub's light and dark palettes; it changes with the Appearance (a MutationObserver on `<html>`, restyling only when the colours did). Type: Geist Mono at 13 px, line height 1.15, falling back to SF Mono, Menlo and a Nerd Font's symbols where installed. The block cursor blinks, outlined when the window is not in use.

## 3. How it works

**The host** (`apps/desktop/src/main/terminal/host.ts`, built as `out/main/terminal-host.js`): a utility process, started with the first terminal opened, that runs every shell on a pseudo-terminal (node-pty). The sessions — output, flow control, replay, lifetime — are `terminal/sessions.ts`'s (`TerminalSessions`, tested with stand-in shells and mirrors); `host.ts` is their wiring to node-pty, the headless terminal, the disk and the ports. Apart from main, a shell pouring out output, or a native module failing, never stalls the window. Main's half (`terminal/service.ts`, `TerminalService`) forks it, hands the shell window one end of a `MessageChannelMain` (`terminalConnect` → `terminalPort`), and is then off the path of every keystroke and byte of output. The preload keeps its end (`terminalSend`, `onTerminalEvent`), queues requests until the port comes, and asks again after the host stopped (`terminalHostGone`: every terminal says so, and Enter starts a new shell — the host is started again only when asked, never in a loop).

**The port** (`TerminalRequest`, `TerminalEvent`): `open` (the shell started if it is not running, in the folder asked, else where it last was, else home; answered by `opened`), `input` (text; `binary` for a legacy mouse report's bytes), `resize`, `ack`, `release`; `data`, `exit`, `failed`. Output is gathered for 5 ms per send. **Flow control**: the renderer acknowledges output as xterm.js has drawn it (every 5,000 characters); the host stops reading a shell more than 100,000 characters ahead and reads on below 5,000 — so `cat` of a huge file never fills the window's memory, and ⌃C lands at once. The mirror is a reader too: what is written to it and not yet drawn is counted (each write's callback), and a shell is held back while its mirror is more than 2,000,000 characters behind, until it is within 200,000 — the window and the mirror both, a shell read only when neither is behind. (Without it, a program pouring output into a terminal nobody draws ran the headless terminal past xterm.js's 50 MB of pending writes, which throws — in the host, taking every shell with it; a write it would still refuse is dropped from the copy, not the host.) For the window, only a shell a window has open (**attached**) is held back: a window that lets a terminal go (`release` — its tab left the snapshot, another Profile in front), loads again (a new port) or closes detaches it, and a build or a server in a terminal nobody draws runs on, its output kept by the mirror. (Before the release, a Profile switch left the host sending to a window that no longer acknowledged, and the shell paused for good at 100,000 characters.)

**The mirror** (`terminal/mirror.ts`). Each shell's output is also drawn into a headless terminal in the host (`@xterm/headless`, 5,000 lines of scrollback), measuring text as the window does (the graphemes addon: an emoji with a variation selector is two cells, so a cursor placed after it lands where the window puts it) and keeping the kitty keyboard protocol's state as the window does. A shell window that loads again (a reload, a crash, a Profile switched back to) opens its terminals and is answered with the mirror's state serialized (`addon-serialize`) — the screen, the scrollback, the alternate screen and its modes — at the size it was drawn, then the size the window has; the serialize addon leaves three things out, which the replay's tail puts back (`replayTail`): the keyboard protocol's state (`kittyRestore`: the stack's bottom set, the rest pushed, the flags in force pushed last, on the screen in use — read from xterm's core, which no public API exposes; the other screen's stack is not restored), the mouse reports' encoding (SGR, `?1006`/`?1016`: the addon says a program wants reports, not in which form), the cursor a program saved (ESC 7: its place, look, origin and wraparound modes — saved again in the window by going there and saving, on the screen in use; the other screen's is not), and the cursor, which origin mode and the scrolling margins send home (the replay writes them itself, after the screen, then puts the cursor back — counted from the margins' top in origin mode — and a pending wrap, the cursor past the last column, made again by printing that column's character again in its own look, then the pen's; the modes that move nothing come last). And a replay ends with the sequence the output broke off in the middle of, if it did (`unfinishedSequence`: the empty write a replay waits on means everything before it was read, not that the reading ended between sequences), so what follows completes it in the window as it does in the mirror. (The empty write's callback is the cut: everything before it is in the replay, everything after follows it.) The mirror is also where the shell's OSC 7 reports are read: each terminal's folder is kept in `terminal/places.json` in the app's data, so a terminal reopened after a restart opens there — the folder it started in is kept at once (a terminal opened in another's folder, never `cd`ed, reopens there too); a folder no tab has named for 14 days is forgotten.

**One screen, two copies.** The window's terminal and the host's mirror must hold the same thing, or a reload replays something the person never saw. So every `opened` makes the window exactly the mirror (reset, then the replay — empty for a shell new to the host: one started again after the host was lost, or for a tab back from the closed), nothing is written into the window's text but the shell's output (why a shell stopped is a note beside it), and ⌘K is not the window's own clear: the host puts `TERMINAL_CLEAR` (a private OSC, 7775) into the output where it stands, and both terminals clear there. The host says `closed` when it closes a terminal; a window whose tab came back meanwhile (⌘⇧T inside the moment between the host's close and the window's letting go — a new tab, found by its address) opens it anew.

**Notices while nobody draws.** A terminal in a Profile not in front has no window: the mirror watches for what the window would have said — a program's OSC 9 or 777, a command of ten seconds or more ending — and the host sends it as a `notice` (only while the mirror answers for the terminal), which the window shows with the terminal's tab's name (kept after the terminal is let go).

**Questions while nobody draws.** A program asks the terminal things (where the cursor is — `CSI 6 n` —, what the terminal is, the kitty flags) and waits for the answer. While a window has the terminal, the window's xterm.js answers; while none has it (released, or a reload under way), the mirror's answers are written to the shell — never both, or a program would read two. Who answers changes hands where the output does, not at the request: the mirror draws behind, so a question it is still drawing as a window opens the terminal is still the mirror's (the window never sees it — the replay is the screen, not the question), and output sent to a window before it let go is the window's. The hand-overs are written into the mirror's stream as they are made and take effect in that order (a release's always; a replay's only if it is still the window's latest), so a window gone and back before the mirror has drawn anything still leaves the mirror the questions it never sent. To keep that true, a window's output reaches the mirror only as it is sent: gathered and never sent when the window lets go (the 5 ms batch), it goes to the mirror after the release's boundary, the mirror's to draw and to answer. (The mirror's clear, ⌘K's, is drawn in its place among the writes too: xterm.js's `clear()` acts at once, on what is drawn so far.) A window that loads again while a terminal's shell is still starting is the one it starts for: its `open` takes the pending start over.

**Ended.** When a shell ends, what its last program left on is put back in the mirror (`terminalModesReset`, the same sequences the window writes: its own screen left, synchronized output ended, a soft reset — DECSTR, which in xterm.js puts back the scrolling margins, origin mode, every private mode, the cursor's style, both screens' kitty flags and the colours — and the mouse reports a soft reset leaves on), after everything it said, so a replay never hands a dead program's modes to the next shell. A session keeps how its shell ended (`exit`), and its mirror: a window opening it again is replayed its screen and then that `exit` (said after the `opened`, never before it, even when the shell ends while the replay is being made); only `open` with `restart` (the person pressed Enter) starts a new shell — in the same session, its mirror going on under it. Before, any `open` of an ended terminal started a shell, so one that ended while its Profile was away came back as a fresh shell: a clean `exit` never closed its tab, a failure's output was gone.

**Lifetime.** Main tells the host which terminals tabs name, on every tab publish (`retain`, every Profile's tabs; only when the set changed): a shell no tab names is hung up on 1.5 s later (SIGHUP; SIGKILL 3 s after if it shrugs it off). Only `retain` keeps a shell — a window opening it again does not — and a shell started after main said no tab names it (a tab closed while its shell waited for the integration, or a window's late `open`) is closed the same way. Quitting takes the host, and every shell, with it.

**node-pty** 1.2.0-beta.15 (pinned, VS Code's): its prebuilt binary is Node-API, so Electron needs no rebuild (`npmRebuild: false` stands), and this beta ships `spawn-helper` executable (1.1.0's lost the bit: `posix_spawnp failed`). It is the app's first native module: `electron-builder.yml` unpacks it (`asarUnpack: **/node_modules/node-pty/**`) — its `.node` loads from a real file and its helper is executed; node-pty finds the helper under `app.asar.unpacked` itself. Checked with an unsigned `--dir` build: the packaged app loads node-pty, the mirror and serialize from its archive and spawns a shell. Signing covers the unpacked binaries (electron-builder signs every Mach-O); notarization of a signed build is not yet verified.

## 4. The shell

**Its environment** (`terminal/environment.ts`, pure): the app's own — what launchd gave it, or the terminal `pnpm dev` ran in — less what is the app's alone (Electron's switches, `NODE_OPTIONS`, the package manager's `npm_*`, `PISTACHIO_*`, the workspace `.env`'s keys — `workspaceEnvironmentKeys`, the keys `loadWorkspaceEnvironment` added) and what belongs to another terminal (`TMUX`, `TERM_PROGRAM`, iTerm's, Ghostty's, kitty's, VS Code's…): a shell that inherited those would think it was inside tmux, or iTerm. To that: `TERM=xterm-256color`, `COLORTERM=truecolor`, `TERM_PROGRAM=Pistachio`, `TERM_PROGRAM_VERSION`, and `LANG=<locale>.UTF-8` when the app was given no locale (a Mac app is not). The host is forked with this environment, and shells start from it.

**Its integration** (`terminal/shell-integration.ts`): written by the host into `terminal/shell-integration/` (a shell cannot read the app's archive), only what changed, whole-or-not-at-all. It reports the folder (OSC 7, percent-encoded byte by byte), the prompt and command marks (OSC 133 A, C, D with the status) and the tab's name (OSC 2).

- **zsh** (`-l`): ZDOTDIR points at ours only so zsh reads our `.zshenv` first; it puts the person's ZDOTDIR back (`PISTACHIO_USER_ZDOTDIR`), sources their `.zshenv`, and for an interactive shell our hooks (`add-zsh-hook precmd/preexec`) — everything zsh reads after is the person's own, from where it always was.
- **bash** (`--init-file`): a login bash reads only its profiles, so ours reads what a login bash reads (`/etc/profile`, then the first of `.bash_profile`, `.bash_login`, `.profile`) and hooks `PROMPT_COMMAND` (folder, name, prompt mark; no command marks: bash has no preexec without a DEBUG trap). Written for macOS's bash 3.2: its bracket ranges take a UTF-8 lead byte for a letter, so bytes are compared by value.
- **fish** (`-l`): our folder first in `XDG_DATA_DIRS` so fish reads `vendor_conf.d/pistachio.fish`, which takes it out again and hooks `fish_prompt`/`fish_preexec`/`fish_postexec` and `PWD`.
- Any other shell: started as a login shell where it takes `-l`, with no integration.

## 5. Security

The port is the shell window's alone: main hands it only to the shell's own contents (`isShell`), and requests are checked (`isTerminalRequest`: the id's form, sizes in bounds, an absolute folder). A page never makes itself a terminal: `will-navigate` to `pistachio://terminal/…` is refused, so is a server's redirect to one (`will-redirect`, which `will-navigate` never sees), and so is a window opened to one (a terminal is started by the person — ⌘J, the menu, the palette, the address bar — never by a link). A terminal's own reads of the clipboard (OSC 52 `?`) are answered empty — by the window, or by the host's copy while no window has it; its writes go through, made by the host (its copy sees every byte of output once, drawn or not) and written by main (`clipboard.writeText`, at most a million characters): a page's clipboard refuses a window without the focus, and a terminal in the background copies too.

## 7. Not done / open questions

- **Settings.** No section yet: the font, its size (only ⌘+/⌘−), the theme, the cursor, Option as Meta (emacs users want it; Ghostty's `macos-option-as-alt`), scrollback. Reading a Ghostty config (`~/.config/ghostty/config`: font, theme from Ghostty's own theme folder) would make Ghostty users at home at once.
- **Ligatures**: the ligatures addon reads font files through Node; the shell has no such reach yet.
- **Close confirmation**: closing a terminal whose shell is running a command (a dev server) ends it without asking; Ghostty asks (`confirm-close-surface`). The renderer knows a command is running (OSC 133 C without D) only where the integration runs.
- **Files dropped on a terminal** open on the desk (the desk's drop zone takes every file drag), rather than typing their paths into the shell as Ghostty and iTerm do.
- **A context menu** (Copy, Paste, Clear, Find) on a right click; right click selects a word only.
- **Progress** (OSC 9;4, which Claude Code and others send) is ignored; it could ring the window or the row.
- **Inline pictures** (Kitty graphics, iTerm's OSC 1337, SIXEL) are not drawn — a program asking finds no support and falls back. They were, with xterm.js's image addon, until a review found the cost: a picture moves the cursor by its size in pixels, which the host's copy of the screen (headless, with no font to measure) cannot know, so the text after a picture landed elsewhere in the two, and a reload replayed it wrong (the addon could also hold the parser while it decoded). Bringing them back means the host knowing the window's cell size in pixels and placing a picture's cells as the window does — or the window telling the host where the cursor went. (SIXEL would need WebAssembly as well, which the shell's CSP refuses.)
- **Splits inside a terminal window**: the desk's tiling is the split; there is no split within one window.
- **The agent** sees a terminal as a tab named after its folder, nothing more; reading a terminal's text (the host's mirror has it) and typing into one are for later, behind the person's say-so.
- **Duplicating a terminal's tab** shows the same terminal in two tabs (the last shown holds it); it should open a new terminal in its folder.
- **fish's integration is untested** (no fish on the machine it was written on).
- A stray `o-` once appeared after vim exited in the e2e run (a terminal reply echoed by the tty after the program left?), not reproduced in two runs since.
- **Kitty keyboard protocol**: xterm.js's is new — its open issues (Option+punctuation, IME commits) are ours while a program has it on.
- Shells end with the app; a session that outlives a quit (tmux-like) would need the host to outlive the app.
